    DeepSeek Harness 核心流程分析

    项目定位

    DeepSeek Harness（CLI 名称 dsh）是 DeepSeek AI 开发的开源 Agent 运行时框架，MIT 协议，TypeScript + Cordis 插件架构。核心理念：一切皆插件——模型、工具、技能、会话、沙箱、存储、Agent 循环、调度器、甚至 UI，全部是可替换的 Cordis 插件。发布首日 5.5 万 GitHub Star，被称为 GitHub 史上最快涨星项目。

    五部分核心组件

    DeepSeek Harness 的核心组件可以分为 5 个部分：

    1. 上下文工程：append-only 会话日志（模型看到的每一条消息都可从日志重构，运行时不变量断言验证）、四种运行模式（Standard/Code/Minimal/Creator）不同上下文策略、Trajectory 视图按来源查看日志
    2. 工具/插件系统：Cordis 微内核（只负责插件挂载/卸载/依赖管理）+ 一切皆插件（模型适配器、工具注册表、技能系统、沙箱、存储、Agent 循环、调度器、UI 全部可替换）
    3. 状态持久化：append-only 事件日志（单一日志文件，支持 resume/fork/search/replay）、插件化存储层、会话状态管理
    4. 权限/安全模型：fail-closed 沙箱阶梯（read-only → workspace-write → danger-full-access，拿不到沙箱后端就拒绝执行）、argv wrapping 命令限制、审批服务缺失即拒绝
    5. 可观测性和审计：会话日志即不变量（运行时断言验证 outgoing request 与 session.deriveMessages() 字节匹配）、无 Key 回放测试（真实会话日志作为 fixture，mock 模型确定性回放）、Trajectory 视图

    一次完整请求流程

    用户通过 Web UI（http://127.0.0.1:3080）或 CLI 发起请求。

    第一步：插件加载与模式选择。 Cordis 微内核加载配置的插件集。四种预设模式加载不同插件组合：Standard（完整编码 Agent，文件编辑+shell+搜索+技能+规划+子Agent+工作流）、Code（Standard 全部能力 + Code Mode SDK，模型生成 TypeScript 程序组合多步操作）、Minimal（只有持久化 bash + str_replace_editor，模型评测脚手架）、Creator（Standard + 运行时检查 + 内存中插件实验）。

    第二步：构建系统提示词。 根据运行模式注入对应的工具描述和技能列表。Minimal 模式只有两个工具的描述，Standard 模式注入完整工具目录。

    第三步：Agent 循环。 插件化的 Agent 循环（本身也是 Cordis 插件，可替换）。模型接收用户输入 → 推理 → 输出工具调用或文本响应。工具调用时：解析调用 → 沙箱策略匹配 → 执行 → 结果追加到上下文。

    第四步：工具执行与沙箱。 工具执行按调用解析沙箱策略：read-only（只读）、workspace-write（推荐默认）、danger-full-access（完全访问）。Linux 优先探测 bubblewrap，回退到原生 Landlock 启动器；macOS 使用 seatbelt；Windows 使用 write-restricted token。关键设计：fail-closed——如果请求了受限模式但没有可用的沙箱后端，直接抛 SANDBOX_UNAVAILABLE 拒绝执行，不会裸奔。

    第五步：会话日志记录。 每次 LLM 调度时，packages/core/agent-loop/src/invariant.ts 中的断言验证 outgoing request 的 messages 与 session.deriveMessages() 字节匹配。记录内容包括：系统提示词、思维链（reasoning）、工具调用与结果、子 Agent 调度、每一次上下文注入。

    第六步：上下文压缩。 当上下文接近窗口限制时，触发压缩策略。具体实现取决于加载的插件组合。

    第七步：子 Agent 调度。 支持生成子 Agent 处理子任务。子 Agent 的调度记录同样写入 append-only 日志。

    第八步：返回结果。 流式推送 Agent 输出到 Web UI 或 CLI。

    关键设计决策

    1. 一切皆插件。 连 Agent 循环都是可替换的 Cordis 插件。这在所有 Agent 框架中是独一无二的——大多数框架的 Agent 循环是核心，不可替换。DSH 把它降维成了一个插件。

    2. 会话日志即不变量。 模型看到的每一条消息，都必须能从 append-only 会话日志中重构。这不是约定，是运行时强制执行的——每次 LLM 调度时断言验证。这是目前 Agent 运行时工程中最有纪律性的设计之一。

    3. 四种运行模式。 Standard（生产）、Code（批量操作）、Minimal（评测）、Creator（开发）。Minimal 模式是最大的看点——只有 shell 和文件编辑器，最小化 harness 优势来做公平的模型对比。DeepSeek V4-Flash 的发布 benchmark 就是用 Minimal 模式跑的。

    4. Fail-closed 沙箱。 拿不到沙箱后端就拒绝执行，不会降级为裸奔。缺少审批服务同样意味着拒绝，而不是挂起。这是安全设计的黄金标准。

    5. 无 API Key 的测试回放。 真实会话日志作为 fixture，从中派生确定性 mock 模型。同一个 .jsonl 日志文件既是 replay 输入又是期望输出。CI 中不需要 API key，不需要不稳定的 LLM-as-judge。循环行为的任何偏移都会表现为日志 diff。

    6. 模型无关。 默认 catalog 支持 DeepSeek V4，但模型适配器是插件，支持 Anthropic、OpenAI、Bedrock、Vertex、Azure、Codex、自定义端点。第一天就支持竞品模型。

    7. 沙箱升级作为模型 UX。 bash 工具的描述教会模型：被拒绝是一种策略结果，正确的应对是在同一轮重试时带上更宽的 sandbox_permissions 和 justification，触发用户的审批提示。

    8. 1M 上下文 + 256K 输出。 默认模型参数：上下文窗口 1,000,000 token，最大输出 256,000 token。这是 DeepSeek 自己的工具链对 V4 的假设。

    9. vendored Cordis fork。 DeepSeek 不仅依赖 Cordis，还 source-vendored 了一个 fork，pin 在 cordis 4.0.0-rc.7，打了 18 个本地 patch，重命名到 @deepseek-ai scope 下，完全拥有框架层。

    DeepSeek Harness 源码与运行流程深度解析

    摘要

    DeepSeek Harness（CLI 名称 dsh）不是一个把“提示词、模型调用、几个工具”写进单体循环的轻量 Agent Demo，而是一个以 Cordis 插件运行时、事件溯源 Session、可替换能力接缝和可逆生命周期 为中心的 Agent Harness。它的核心设计不是“某个 Agent 类足够强”，而是“模型适配器、系统提示词、工具注册表、执行环境、审批、压缩、会话持久化、子 Agent、Web/SDK 入口乃至 AgentLoop 本身都可作为插件组合、替换和卸载”。

    一次典型任务的主链是：

    1. dsh CLI 解析 profile、环境变量和 patch；
    2. profile 将 bundle、用户 patch、全局 patch 和命令行 patch 叠加为 Cordis 插件树；
    3. Agent 创建事务同时准备 Session、Agent scope 和持久化写句柄；
    4. ReactLoopAgent 从 inbox 领取输入，组装提示词和工具 schema；
    5. LLM adapter 绑定本次调用配置并流式返回 reasoning、text 和 tool call；
    6. 工具调用经过准入、审批、单调 guard、执行、结果转换、spill/压缩等流水线；
    7. 所有模型可见事实写入 append-only Session log，再由 surface 投影得到下一次模型请求；
    8. 当上下文承压时，先处理超大工具结果，再裁剪历史工具结果，最后摘要旧历史；若仍没有可安全压缩的区域，则保留并返回 CONTEXT_WINDOW_EXCEEDED，不会无上限重试。

    最值得借鉴的工程思想有三点：

    • 模型可见即日志可重建：进入模型请求的状态必须由 Session log 重建，不能只藏在内存变量里。
    • 插件而非修改 Loop：新能力优先挂到 service、event、tool pipeline 或 profile 层，不直接扩张核心循环。
    • 大结果不等于摘要 50%：当前工具结果采用 spill + 首尾预览；历史工具结果采用确定性裁剪；整个历史才采用模型摘要。三层策略解决的是不同阶段的问题。

    2. Harness 到底负责什么

    模型只负责根据输入产生输出或工具调用意图。Harness 负责模型外层的工程系统：

    • 选择 provider/model 和解析配置；
    • 构建 system prompt、上下文和工具 schema；
    • 管理 turn、step、重试、取消和停止条件；
    • 校验、授权和真正执行工具；
    • 管理文件系统、进程、终端、沙箱与审批；
    • 记录可恢复的会话历史；
    • 控制上下文窗口、工具结果、图片和压缩；
    • 管理子 Agent、后台任务、工作流和 UI/SDK 接入；
    • 提供日志、回放、测试与安全边界。

    3. 架构总览：Everything is a Plugin

    3.1 Cordis 的五个核心概念

    Cordis 在 DSH 中提供以下基础语义：

    1. Plugin：函数插件或 Service 子类；
    2. Context：按稳定 key 提供服务，例如 ctx.llm、ctx.tools、ctx.sessions；
    3. Inject：插件声明依赖，依赖满足时才激活；
    4. Typed Event：通过 emit、waterfall、parallel、serial、bail 等模式连接插件；
    5. Effect：注册行为带 disposer，插件卸载时按生命周期撤销。

    官方架构文档明确指出：模型适配器、工具注册表、Session log 和 AgentLoop 本身都是插件，没有需要不断打补丁的“特权核心”。Architecture

    Cordis 论文将其理论基础概括为时空可组合性：

    • 时间可组合性：组件移除时能撤销其副作用；
    • 空间可组合性：组件声明依赖，并随上下文变化激活或停用；
    • 二者通过统一 Context 协调。

    论文并没有逐一规定 DSH 的 service、AgentLoop 或工具协议；这些是 DSH 在 Cordis 机制上的具体工程映射。

    3.2 Service、Provider、Consumer

    DSH 把可替换能力建模为 capability seam：

    Service Definition  ->  Service Provider  ->  Consumer
接口声明                具体实现               工具/Agent/UI 调用者

    例如文件能力：

    ctx.fs 接口 -> Local / Sandbox / SSH FS Provider -> read/write/edit 工具

    例如进程能力：

    ctx.subprocess -> Local / Remote Provider -> Bash / Terminal / LSP

    Consumer 依赖接口包，不依赖具体 provider。这样把本地 provider 换成 SSH/远程沙箱后，Shell、PTY、LSP 可以整体迁移到同一个“执行世界”，而无需复制 AgentLoop。

    4.6 为什么可热更新、可回滚

    工具、Prompt section、模型 adapter、event listener 等注册通过 ctx.effect() 或 ctx.on() 返回 disposer。插件卸载时 Fiber 执行逆向清理；HMR 重新应用完整 patch generation，并等待旧 Fiber dispose 与新树稳定。启动失败不会让半棵插件树继续运行。

    这就是 Cordis “时间可组合性”在 DSH 中最直接的体现。

    6. Agent 创建：一个回滚覆盖的事务

    6.1 关键对象

    • AgentRegistry：保存 live Agent，代理 create/resume，使用 AsyncLocalStorage 传播当前 initiator；
    • AgentLoop：实现 AgentFactory，创建/恢复 Session 和具体 driver；
    • ReactLoopAgent：运行 turn/step 状态机；
    • SessionStore：保存 live Session；
    • SessionPersistence：持久化 provider；
    • Scope：每个 Agent 独立的插件注册作用域。

    6.2 创建事务顺序

    AgentLoop.createAgent() / create() 的主要顺序是：

    SessionStore.prepare()
  -> 若有 persistence，先获取 write handle
  -> prepare(): 构造 ReactLoopAgent + agent scope + memoized dispose
  -> 可选 setup(agentCtx, agent)
  -> setupCommit.commit()
  -> 写入尚未持久化的 Session suffix
  -> sessions.enter(session)
  -> agents.enter(agent)
  -> sessions.announce(session)
  -> await agents.announce(agent, source)
  -> 返回 AgentHandle

    任何 setup、commit、持久化或 agent/created listener 失败，都会沿同一个 dispose 边界回滚。Teardown 的逻辑顺序为：

    取消 Agent
  -> 等待 driver idle
  -> dispose agent scope
  -> 关闭并 drain Session write handle
  -> detach Agent
  -> detach Session

    7.2 Inbox 与唤醒

    ReactLoopAgent 的阶段状态为：

    idle | maintenance | running
    • followup()：写入 next-turn 并唤醒；
    • steer()：写入 next-step 并唤醒；
    • inject()：写入 next-step，但不主动唤醒；
    • cancel()：可清 inbox，并 abort 当前 controller。

    wakeDriver() 只创建一个 driver。非 idle 时新的 wake 会被当前 driver 接管，或在 maintenance/已 abort 场景下置为 wakeRequested，待当前 activity 收敛后重放。

    源码：packages/core/agent-loop/src/agent.ts:121-240

    7.3 Turn

    turn() 的核心流程：

    1. 追加 turn/start；
    2. 首次从 next-turn 原子领取输入；后续 step 只领 next-step；
    3. preStep() 组装 Prompt，并触发 agent/pre-step waterfall；
    4. reject 则以 blocked 结束；首次输入被改写为空则零 step 完成；
    5. 追加 step/start；
    6. 调用 step()；
    7. 无论成功失败均追加 step/end；
    8. 若暂时没有 next-step 输入，触发 agent/turn-stopping；
    9. 无待处理工作则 turn/end；仍有 next-turn 输入则复用 driver 开下一 turn。

    源码：packages/core/agent-loop/src/agent.ts:266-378

    7.4 Step 与模型调用

    step() 中最重要的顺序约束是：

    agent/request
  -> llm.prepareCall()
  -> 根据实际 prepared route 协调 system prompt
  -> 首次 attempt 写入 user/message
  -> 记录 request/header 与 request/context
  -> Session.deriveMessages()
  -> 冻结请求
  -> preparedCall.stream()

    agent/request 和 prepareCall() 完成前，待接纳的 system/user 输入还没有写入历史；若此时取消，不会留下半接纳输入。Retry 重用同一次 assembly 和 user admission，不再次执行 agent/pre-step。

    流式返回由 AssistantStreamAttempt 收集：

    • 成功：落 assistant/message，保留完整紧凑 stream 与 usage；
    • 失败/重试：落 assistant/attempt，不进入模型历史；
    • 中途取消且已有可见输出：落 assistant/message(interrupted: true)，保证下一请求看到用户已经看到的前缀。

    若消息没有 tool call，则 step 完成；否则进入 executeToolCalls()。

    源码：packages/core/agent-loop/src/agent.ts:380-526

    prepareRequest()：

    • 从 AgentOptions 和最近 request header 建议 provider/model；
    • 移除 adapter 自动补的默认项，让下一次 route 重新解析；
    • 允许 agent/request waterfall 改写配置；
    • 调用 ctx.llm.prepareCall() 绑定 adapter；
    • 缺 provider/model 立即失败。

    buildRequest()：

    • 规范化并按需追加 request/header；

    8. 工具系统

    8.1 Schema 如何进入模型

    工具插件通过 ctx.tools.register() 注册。每次 system prompt assembly 时，ctx.tools.schemas(scope) 投影当前 Agent 可见的 schema。模型只会看到：

    • name；
    • description；
    • parameters；
    • 可选 deferLoading。

    执行函数、超时、输出渲染器和 UI presenter 不会上 wire。Agent scope 的 restrict()、同名 shadow 和插件卸载都会改变最终可见工具集。

    8.2 固定执行流水线

    一个工具调用依次通过：

    参数解析与冻结
  -> tools/pre-execute
  -> monotonic guards
  -> tools/execute around-waterfall
  -> ToolDefinition.execute()
  -> output schema validation/render
  -> projectContent
  -> tools/post-execute
  -> finalizeContent
  -> tools/result observer
  -> Session tool/result

    关键性质：

    • pre-execute 可 allow / deny / ask / cancel；
    • guard 是单调拒绝，后续插件不能把 deny 改回 allow；
    • tool throw、unknown tool、deny 都变成结构化 error result，通常不会直接结束 turn；
    • timeout 由外部 dsh-tool-call-timeout-policy 执行，ToolDefinition 里的 timeoutMs 只是声明；
    • 取消是 cooperative；工具必须响应 signal，timeout 也不是强制杀线程。

    参考：Tools README

    8.3 并发调度

    executeToolCalls() 先把模型输出解析为 planned calls：

    • exclusive 调用单独形成 barrier；
    • parallel 调用进入有界 rolling pool；
    • 默认每 step 最多 10 个并发安全调用；
    • dispatch/body 可以并发，但 pre-execute、结果 finalize、Session commit 按模型顺序；
    • 在后续 call 启动前重新读取 execution mode，插件热变更可把它变为 barrier；
    • 取消后停止补充新调用，等待已启动调用收敛；未启动调用写入 ABORTED_BEFORE_DISPATCH 配对结果，保证 replay 合法。

    源码：packages/core/agent-loop/src/tool-calls.ts:60-102、122-247

    8.4 PTC 模式

    工具可按 native、ptc 或 both 呈现。PTC 模式不是直接给模型所有工具 schema，而是暴露 run_code 和生成的 SDK，让模型编写一次短程序并在程序内调用多个工具。

    它适合：

    • 多个独立读取并发；
    • 中间结果不进入对话；
    • 只抽取最后所需字段；
    • 减少多轮 “调用—回传—再调用”。

    但中间值是执行态内存，不进入 Session replay，且可能消耗内存；只有外层 run_code 结果有硬大小限制。

    9. Session：模型历史的唯一事实源

    9.1 Append-only Event Log

    Session 采用连续 seq 的 append-only 事件日志。核心事件包括：

    • 生命周期：turn/start、turn/end、step/start、step/end；
    • 模型表面：system/message、user/message、assistant/message、tool/result；
    • 追踪：assistant/attempt、tool/call；
    • 请求：request/header、request/context；
    • seed/fork 边界：session/end-seed；
    • 插件通过 declaration merging 扩展事件类型。

    Session.append() 先做 lossless JSON snapshot、事件数据校验和 surface transition 校验，确认合法后再加入 log；observer 失败只记录，不反向撤销已提交 append。

    源码：packages/core/session/src/index.ts:683-771

    9.2 Surface：Append-only 日志上的可替换视图

    日志不可删，但模型历史需要压缩和替换。DSH 通过 surfaceOp 构建可替换 surface：

    'append'
| { op: 'replace', startSeq, endSeq }

    替换事件必须：

    • 指向当前 surface 中连续存在的节点；
    • sourceEventSeqs 包含所有被 shadow 的节点；
    • 不能任意改写 system head；
    • tool-result replacement 只能改内容，不能偷偷改变 call id、错误状态等语义。

    因此，原始历史仍在日志里，下一次模型请求只看到 surface 投影后的版本。

    源码：packages/core/session/src/types.ts:430-478、packages/core/session/src/surface.ts:515-590

    9.3 deriveMessages()

    Session.deriveMessages() 遍历 surface 节点，把五种 message-producing event 转成模型消息；turn/step、失败 attempt 等日志事件不会进入模型上下文。纯 append 只增量处理新节点；一旦发生 replacement 或消息投影，contentGeneration 变化并触发重建。

    源码：packages/core/session/src/index.ts:817-873

    9.4 “Model-visible ⟺ Logged”

    这是整个设计的关键不变量：任何进入模型请求的输入，都必须能从 Session log 和注册的纯投影重建。否则：

    • resume 后行为会漂移；
    • fork 无法保持语义；
    • telemetry、回放、测试和 UI 会看到不同事实；
    • 压缩前后无法证明来源。

    10. DeepSeek 模型适配器

    10.1 Provider 路由

    LlmRuntime 按 provider 名注册 adapter。DeepSeek 官方插件注册路由 deepseek-official。prepareCall() 把一次调用的：

    • 连接配置；
    • 模型能力；
    • 默认 reasoning/maxTokens；
    • retry policy；
    • system prompt update 模式

    绑定为 PreparedLlmCall，防止请求进行中配置热更新造成半次调用使用两套参数。

    10.2 Wire 协议

    当前 adapter 使用 DeepSeek Messages-compatible endpoint，核心行为包括：

    • 文本、thinking、tool call、tool result 作为 content blocks；
    • reasoning effort 映射到 output_config.effort；
    • 流响应使用 SSE；
    • SSE 的 event 名和 JSON type 必须一致；
    • text/thinking/tool_use delta 转成统一 Harness stream chunk；
    • 结束时输出 usage、finish 和 replay metadata；
    • 过早 EOF 归一为 STREAM_CLOSED。

    Adapter 识别并标准化 AUTH、RATE_LIMIT、CONTEXT_WINDOW_EXCEEDED、SERVER、TIMEOUT 等错误，使上层 retry/compaction 无需解析脆弱的自然语言。

    官方 package 文档：dsh-llm-deepseek README

    10.3 默认模型容量不是整个系统的承诺

    该版本默认 catalog 为部分模型声明 1,000,000 token context window，并把 adapter maxTokens 默认设为 256,000；但实际可用模型、网关能力、计费和上下文上限仍由目标 endpoint 决定。Harness 使用 adapter 暴露的 capacity 做 compaction 规划，provider 最终响应仍是权威事实。

    11. 上下文窗口与大工具结果：三层防线

    这是理解 DSH 最有实践价值的部分。

    11.1 第一层：当前工具结果 Spill

    工具执行完成后，dsh-spill-policy 在 tools/post-execute 阶段处理当前结果：

    1. 计算文本与图片的共享预算；
    2. 超预算时将完整格式化结果存入 SpillStore；
    3. 模型只看到按原顺序保留的头部/尾部；
    4. 加入遗漏字节数、图片数和完整结果路径；
    5. 模型随后可用 read(offset, limit) 或 grep 按需读取。

    默认 maxInlineTokens = 12500。所谓“50%”不是把完整结果压缩到 50%，而是扣除 notice 成本后，把剩余预览预算大致平分给头和尾。

    如果连 notice 都放不下，或者 storage/owner/image pricing 不可用，策略 fail-open：记录警告并保留原结果，避免返回一个模型无法访问的假路径。

    参考：Spill Policy README

    11.2 第二层：历史 Tool Result Pruner

    当整个对话接近压力阈值，compaction 前先运行工具结果 pruner。默认对超过 8,192 字符的历史 tool result：

    • 头部保留 4,096 字符；
    • 尾部保留 1,024 字符；
    • 中间替换为 marker；
    • 使用 surface replacement 写入可回放的新结果。

    它不调用模型，成本低、结果确定，常常可直接让请求重新回到阈值内。

    11.3 第三层：Conversation Compaction

    若 pruning 后仍超阈值，dsh-compaction-basic：

    1. 用同一个 token meter 计算压力；
    2. 从 system head 之后选择最老、语义平衡且可安全替换的 span；
    3. 保留最近历史；
    4. 额外调用一次模型生成结构化 checkpoint；
    5. 验证摘要确实比原区域更小；
    6. 记录 compaction/start、compaction/summary、surface replacement 和 compaction/end；
    7. 下一次请求只看到 checkpoint + 最近历史。

    默认策略：

    参数 默认值
    thresholdRatio 0.8
    retainRatio 0.16
    headroomTokens 65,536
    maxTokens 65,536 或解析后的 headroom
    compactionRetries 1
    maxOverflowRetries 1
    auto true

    触发阈值：

    floor(min(W × 0.8, W − O − 65536))

    其中 W 是 context window，O 是本次输出预留。

    11.4 Provider 明确报超窗时

    收到 CONTEXT_WINDOW_EXCEEDED 后，自动恢复会：

    • 绕过普通 80% 阈值；
    • 先 prune；
    • 把最近保留量降为 0，尝试最大安全 head reduction；
    • 只有 surface replacement generation 确实前进，才授权重试；
    • 默认最多一次 overflow retry。

    11.5 回答“压缩 50% 仍不够怎么办”

    在该源码中，正确答案不是“继续按 50% 无限压缩”，而是：

    当前超大工具结果
  -> Spill 到文件，模型只拿首尾预览和路径
历史超大工具结果
  -> 确定性裁剪
整体历史仍超窗
  -> 摘要最老的安全区域
仍超窗
  -> 检查不可压缩部分：system prompt、tool schemas、prefix、单个不可拆单元
  -> 有新的安全替换区域才有限重试
  -> 无安全区域或重试耗尽，返回 CONTEXT_WINDOW_EXCEEDED

    不能压缩的典型情况：

    • system prompt + tool schemas + 输出预留本身已逼近窗口；
    • 一个不可拆的非工具消息本身过大；
    • 单个 tool call/result 对的不可裁剪部分仍超窗；
    • spill notice 太长而预算太小，导致 spill 替换被放弃；
    • token meter 估算偏差，特别是 CJK 与大型 JSON Schema。

    工程改进顺序应是：

    1. 让工具原生支持分页、字段过滤和句柄；
    2. 降低工具 schema 与 system prompt；
    3. 确保 spill backend 可用，并让 locator 足够短；
    4. 单独调整 pruner 阈值和保留长度；
    5. 按模型调整 compaction headroom/retention；
    6. 对不可拆单元改协议，而不是继续摘要；
    7. 最终明确失败，避免无界重试与账单失控。

    参考：Compaction README、自动恢复与限制

    12. 执行世界、安全和权限

    12.1 Shell 路径

    典型 Bash 调用链：

    tool-bash
  -> 解析当前 sandbox policy / 可选一次性升级
  -> ctx.shell.resolve/execute
  -> SandboxBashExecutor.confine(['bash', '-c', command])
  -> ctx.subprocess.spawn
  -> 进程输出
  -> ToolRuntime post-execute/finalize

    danger-full-access 可绕过 confinement；受限模式没有可用 runner 时应 fail closed。

    12.2 文件路径

    文件工具经 ctx.fs；sandbox provider 对 canonical path、父目录和 symlink 做检查；observation policy 增加 read-before-edit 和版本 CAS。需要明确：这是降低风险的用户态约束，不是完整内核隔离。

    一个值得注意的例外是 glob/grep：实现通过固定 ripgrep argv 调用 ctx.subprocess.spawn，不走 shell 字符串；它使用 --no-config 避免宿主 ripgrep 配置注入。

    12.3 审批

    权限升级只有严格更宽的模式才需要审批；缺少审批服务、无 Agent、拒绝、取消或无响应都按失败处理。授权是 allowed-once，不是永久扩大 Session 权限。

    默认 profile：

    • read-only：sandbox read-only + ask；
    • workspace-write：sandbox workspace-write + ask；
    • danger-full-access：sandbox danger-full-access + approval never。

    12.4 安全声明

    官方 SAFETY 明确指出：项目尚未安全审计，不能视为生产安全软件；它能执行模型生成的命令、加载第三方插件并访问文件、网络、进程和凭据；沙箱、审批和权限控制只能降低风险，不保证隔离。SAFETY

    生产评估时至少应补充：

    • 一次性 VM/容器；
    • 最小权限与最小文件范围；

    13. 子 Agent、Jobs、Workflow 与 MCP

    13.1 In-process Subagent

    In-process 子 Agent 有独立工具 scope 和 Session。父 Agent 可显式传递 sandbox override 与 tool filter；子 Agent 的 approval 固定为 never，避免它直接弹出人机审批。Delegation depth 持久化到 Session header，防止 resume 后递归预算重置。

    13.2 Fork Subagent

    Fork 模式从父 Session 的某个 event boundary 复制前缀，必要时为开放的 step/turn 添加合成 closer；父子保持共同历史，有利于 DeepSeek KV cache 复用。默认 base 中 fork child 为 one-shot。

    13.3 Jobs

    Jobs 按 Session owner 精确隔离，list/read/kill/wait 均检查 owner；owner dispose 或 archive 时取消任务。它适合把长任务从当前 turn 解耦，但仍需控制每 owner 并发上限。

    13.4 Workflow / PTC

    Workflow 让模型生成 JavaScript，由 PTC runtime 执行并在程序中调用工具。它适合多步固定流程，但 VM 不是强安全边界；应把它视为与 Bash 接近的执行权限，并由 sandbox、审批和环境隔离共同约束。

    13.5 MCP

    MCP server 暴露的工具注册为 mcp__<server>__<tool>，沿用 ToolRuntime pipeline。HTTP MCP 可复用代理策略；stdio MCP 的子进程由 MCP SDK 启动，当前实现不天然继承 ctx.subprocess 的进程树与 shell sandbox，这是一项部署时应单独评审的边界。

    14. 错误恢复与停止语义

    14.1 错误分类

    • 模型适配器错误：结构化 LlmFailure；
    • agent/request-error listener 可决定 retry；
    • tool error：通常转换为 error result，交给模型继续；
    • plugin/middleware/result processing error：结束当前 turn，但 AgentLoop driver 本身被边界捕获，可接受后续工作；
    • process 未处理异常：fail loud，先尝试有界释放资源再退出。

    14.2 取消

    取消使用 AbortSignal，但遵循 cooperative + quiescent：

    • 取消阻止新的模型块或工具开始；
    • 已启动工具需等待其响应取消并收敛；
    • 已经展示给用户的模型前缀要落为 interrupted assistant message；
    • 未 dispatch 的 tool calls 写入合成错误结果；
    • turn/end 记录结构化 cancel cause。

    14.3 无内置 Turn Budget

    AgentLoop 没有内置最大 step/turn 工具调用预算。模型持续产生工具调用或插件持续注入 next-step 时，turn 可继续。需要部署通过 agent/turn-stopping、成本监控或自定义 guard 实现总预算。

    15. 持久化、迁移与可回放性

    当前 writer 的 SESSION_FORMAT_VERSION = 4，但该 checkout 文档记录的最新已发布格式为 V3；V4 已完成兼容基线，但发布记录独立维护。新的 release candidate 也必须把已落地的 Session 数据视为兼容性义务。

    持久化设计要点：

    • JSONL generation 文件不可覆盖旧 generation；

    • 只读打开可在内存迁移；
    • 写打开先编码、验证，再排他发布新 generation；
    • 原始 generation 不重命名、不覆盖、不删除；
    • 未识别且非 ignorable 的事件必须拒绝读取，防止静默丢失语义。

    18.1 产品阶段

    Developer preview，公开 API 和插件组合可能破坏兼容，不宜未经封装直接作为强 SLA 生产基础设施。

    • sandbox 不是完整隔离；

    5–13 分钟：Cordis 与插件架构

    目标

    解释 Context、Service、Inject、Event、Effect，以及它们如何解决大型 Agent 系统的组合问题。

    讲稿

    DeepSeek Harness 构建在 Cordis 上。理解 Cordis，不需要先读完整论文，只要抓住五个概念。

    第一，插件是最小组合单元。它可以是一个函数，也可以是 Service 子类。第二，Context 是服务容器，插件不直接依赖具体实现，而是通过 ctx.tools、ctx.llm、ctx.sessions 这样的 key 找能力。第三，插件用 inject 声明依赖；服务没准备好时，插件等待，而不是靠程序员手写启动顺序。第四，Typed Event 是插件间的拦截和通知机制。第五，所有注册都应该是 Effect，也就是带反向清理动作。

    这里的关键不是“插件多”，而是插件生命周期可逆。比如一个模型 adapter 注册到 ctx.llm，热更新时旧插件卸载，adapter 注册随 effect 撤销；新插件再注册。工具、Prompt section、listener 都遵循同一个模式。

    Cordis 论文把这种思路称为时空可组合性。时间维度解决卸载时如何撤销副作用，空间维度解决依赖变化时组件如何激活和停用。DSH 把这套机制用于 Agent Runtime。

    再看 capability seam。一个完整能力通常有三种角色：Service Definition、Provider 和 Consumer。以文件系统为例，ctx.fs 是接口，Local/SSH/Sandbox 是 provider，read/write/edit 是 consumer。这样把本地 provider 换成远端 provider，AgentLoop 不需要改。

    这也是为什么官方规范强调“插件，而不是改 Loop”。如果我们新增一个模型 provider，应注册到 ctx.llm；新增一个工具，应注册到 ctx.tools；新增工具审批，应拦截 tools/pre-execute。只有改变所有 Agent 的基本 turn/step 语义时才考虑修改 loop。

    20–32 分钟：AgentLoop、Turn 与 Step

    目标

    让听众能沿源码追踪从输入到下一次模型请求。

    讲稿

    核心类是 ReactLoopAgent。它只有三个宏观阶段：idle、maintenance 和 running。用户输入进入 inbox，分成 next-turn 和 next-step。

    followup 是下一轮普通用户输入；steer 是希望尽快进入下一 step 的方向调整；inject 也是 next-step，但不会主动唤醒，适合文件变化或后台上下文等待下一次自然请求。

    Agent 被唤醒后，kick() 循环执行 turn()。每个 turn 先写 turn/start，再领取输入并执行 preStep()。这里先组装 system prompt 和 tool schema，再触发 agent/pre-step waterfall。插件可以拒绝本 step，也可以改写消息，例如压缩插件就在这里检查上下文压力。

    如果输入被接纳，就写 step/start 并进入 step()。一个 step 的定义是“一次模型请求加这次请求产生的工具调用”。

    step() 的顺序非常讲究。先运行 agent/request，再执行 llm.prepareCall()。只有实际 provider route 和能力确定后，才协调 system prompt，写入用户消息，记录 request header/context，然后从 Session 派生 history。

    为什么不先把 user message 写进去？因为 request middleware 或 adapter prepare 可能异步失败或被取消。DSH 希望在真正接纳请求前，日志里不出现一半成功的输入。

    模型流返回时，系统把 reasoning、text、tool call 组装成 AssistantStreamAttempt。成功后落 assistant/message；失败并准备重试时落 assistant/attempt，它用于审计但不进入下一次模型历史。中途取消且用户已经看到一部分输出时，则把可见前缀记录成 interrupted: true 的 assistant message。这样下一次请求知道用户见过什么。

    如果 assistant 没有 tool call，step 完成；有 tool call，就进入工具调度。工具结果写入 Session 后，下一 step 再从 Session 派生完整历史。

    Turn 结束前还有 agent/turn-stopping 扩展点。插件可以在这里注入工作让 turn 继续。因为默认没有总 turn budget，生产部署应该在这里或相邻扩展点加总成本、总步骤、总时长限制。

    过渡

    目前我们看到的日志很多，但模型并不读取整个日志。下面看 Session 如何同时做到“历史不丢”和“模型上下文可替换”。

    32–40 分钟：Session Event Sourcing 与 Surface

    目标

    解释 append-only log、surface replacement 和 deriveMessages。

    讲稿

    DSH 的 Session 不是一个可随意修改的 messages 数组，而是一串 seq 连续的事件。turn、step、user、assistant、tool、request header 都是事件。

    最重要的规则叫 “Model-visible means logged”。任何进入模型的内容都必须能够从日志重建。如果插件偷偷在内存中给 request 拼了一段内容，却不留事件，那么重启、fork、回放、压缩和 UI 都会看到不同世界。

    但 append-only 日志遇到一个问题：我们要压缩历史，怎么删除旧消息？DSH 的答案是不删日志，而是在日志之上维护 surface。

    一个模型可见事件携带 surfaceOp。普通消息是 append；压缩结果是 replace，声明它替换当前 surface 上从 startSeq 到 endSeq 的一段。替换事件还要在 sourceEventSeqs 中列出所有被覆盖节点。

    这样原始事件仍存在，可做审计、回放和迁移；模型只读取 surface 当前节点。

    deriveMessages() 就是这个投影入口。只有 system、developer、user、assistant 和 tool result 进入模型；turn boundary、失败 attempt 等都不进入。纯 append 时增量更新；发生 replacement 时 generation 变化，缓存重建。

    这个设计比直接把 messages 数组就地改写更复杂，但解决了四个问题：可追溯、可恢复、可迁移、可验证。压缩摘要还能明确证明它来自哪些原消息。

    页面/演示

    Event log:  [u1][a1][tool1][result1][u2][summary]
Surface:                                  [summary] replaces u1..result1, then [u2]

    强调原始节点仍在 log 中，只是被 shadow。

    过渡

    有了 Session 事实源，再看最容易失控的部分：工具结果和整个上下文变大时，系统如何逐层处理。

    40–50 分钟：工具流水线与上下文控制

    目标

    回答大结果、50% 压缩仍不够、溢出重试等工程问题。

    讲稿

    先看工具流水线。模型输出的 call 不会直接执行。参数先解析和冻结，然后经过 tools/pre-execute。这里可以做 allow、deny、ask。之后还有单调 guard：一旦拒绝，后续插件不能重新放行。

    真正执行在 tools/execute around-waterfall 中，timeout、retry、metrics 都可以包在这里。执行完成后做 output schema 校验、渲染、projectContent，再进入 tools/post-execute。Spill policy 就挂在 post-execute。最后才运行工具自己的 finalize，然后发布 immutable result。

    工具调度支持并发，但只并发工具 body。准入和结果 commit 仍按模型顺序。Exclusive call 形成 barrier；parallel-safe calls 使用默认上限 10 的 rolling pool。取消时，不再启动后续工具，但会等待已经启动的工具收敛，并为未启动调用生成固定错误结果。

    接下来回答最常见的问题：一个工具结果太大，压缩 50% 仍然塞不进窗口怎么办？

    DSH 并没有一条“所有内容压缩 50%”的规则。它用了三层不同机制。

    第一层是 spill，处理当前工具结果。完整结果写到文件，模型只拿首尾预览和路径。这里的 50% 指剩余预览预算在头尾之间均分，不是压缩比例。

    第二层是 tool-result pruner，处理已经在历史里的大工具结果。默认 8192 字符以上保留头 4096、尾 1024，中间放 marker。它不调用模型。

    第三层才是 conversation compaction，选择最老的安全历史区域，让模型生成结构化 checkpoint，并用 surface replacement 替换旧区域。

    如果 provider 已明确报 context overflow，系统绕过普通阈值，尽可能做最大安全压缩，再有限重试。默认 overflow recovery 只有一次。

    最关键的是：如果不可压缩部分本身太大，例如 system prompt、工具 schema、输出预留，或者只有一个不可拆单元，系统不会无限摘要。没有新的 surface replacement，或者重试耗尽，就保留原始 CONTEXT_WINDOW_EXCEEDED。

    这给我们的工程建议是：大结果首先改工具协议，支持分页、字段过滤、结果句柄和按需读取；不要把所有压力都交给对话摘要。摘要是最后一道防线，不是数据传输协议。

    上下文控制解决“能不能继续跑”，但还没有回答“执行是否安全”。最后看执行世界和安全边界。

    50–56 分钟：执行世界、审批与子 Agent

    目标

    说明 sandbox 不是万能边界，子 Agent 与 MCP 也有独立权限问题。

    讲稿

    DSH 把文件系统和 subprocess 视为同一个执行世界。Bash 最终调用 ctx.subprocess.spawn；在 sandbox 模式下先通过 ctx.sandbox.confine 包装 argv。文件写入通过 ctx.fs 和 sandbox provider 检查 workspace、canonical path 和 symlink。

    默认是 workspace-write 加 ask。权限升级只对更宽权限生效，而且一般是 allowed-once。审批服务缺失、用户拒绝、取消或无答复都失败。

    但官方安全声明非常明确：项目没有安全审计，sandbox 和审批只能降低风险，不能保证隔离。网络、凭据、第三方插件、MCP stdio、VM 中的动态代码都是需要单独评估的攻击面。

    子 Agent 也不是“自动安全”。In-process child 有独立 scope，子 Agent 默认不能直接向用户申请审批；fork child 继承一段历史以复用上下文。外部 ACP/Claude/Codex provider 可能有自己的工具和权限模型，不能想当然地认为父 Agent 的 tool filter 自动覆盖外部 runtime。

    MCP 的 HTTP 路径和 stdio 路径也不同。特别是 stdio 进程由 MCP SDK 启动时，不天然获得 DSH subprocess provider 的完整进程树和 shell sandbox 行为。因此把 MCP server 接进来前要做单独的进程与凭据审计。

    最后四分钟总结这套架构最值得复用的原则，并回答常见问题。

    56–60 分钟：总结与 Q&A 引导

    讲稿

    今天可以带走五个结论。

    第一，Harness 是 Agent 的操作系统层。模型只提出动作，Harness 决定是否执行、如何记录、如何恢复。

    第二，DeepSeek Harness 的核心竞争力不是某个超级 Agent 类，而是插件树、能力接缝和可逆生命周期。它允许模型、工具、存储、执行环境和 UI 分别演化。

    第三，Session event log 是全系统事实源，surface 是模型当前看到的可替换视图。原始事实和模型上下文不再是同一个可变数组。

    第四，上下文治理必须分层。当前大结果用 spill，历史大结果用确定性裁剪，整体历史用摘要；不可拆部分超窗时必须显式失败。

    第五，灵活性不等于安全性。Developer preview、未审计、第三方插件和动态执行决定了生产部署必须增加外部隔离与权限治理。

    如果团队准备借鉴，我建议先复用三项：

    1. Model-visible 必须 logged；
    2. 工具流水线固定阶段化；
    3. 大结果使用外部制品与句柄，而不是持续向窗口塞摘要。

    如果准备直接采用 DSH，则先做三个 POC：

    1. 用自己的模型路由跑一套 recorded session replay；
    2. 用真实大结果验证 spill、pruner 和 compaction；
    3. 在一次性环境验证 sandbox、MCP、凭据与审批的组合边界。

    21. FAQ

    Q1：DeepSeek Harness 与 DeepSeek 模型是什么关系？

    Harness 是模型外层运行系统。它可接 DeepSeek 官方 adapter，也可同时挂多 provider adapter。模型生成文本和工具调用意图，Harness 负责组装请求、执行工具、记录状态与恢复。

    Q2：它和普通 ReAct Agent 最大区别是什么？

    普通 ReAct 示例通常只有一个内存 messages 数组和 while-loop。DSH 还包含插件生命周期、事件溯源 Session、profile composition、工具政策、沙箱、持久化、迁移、压缩、子 Agent、UI/SDK 和测试基础设施。

    Q3：为什么 AgentLoop 也要做成插件？

    因为不同产品可能需要不同驱动语义。UI、工具和 hook 依赖抽象 Agent/AgentRegistry，不应直接绑定默认 loop。

    Q4：为什么不用一个 DI 容器就够了？

    普通 DI 主要解决构造依赖。Cordis 还解决运行中服务出现/消失、插件激活/停用、effect 撤销、事件 waterfall 和 HMR 生命周期。

    Q5：Waterfall 和普通事件有什么区别？

    Waterfall 是 around-middleware。Listener 调用 next() 才把控制交给下游；不调用可短路并返回自己的结果。它适合请求改写、工具策略和 retry 决策。

    Q6：Turn 与 Step 有什么区别？

    Step 是一次模型请求及其工具调用；Turn 从领取一条用户输入开始，可包含多个 step，直到没有工具、steering、goal 或其他 next-step 工作。

    Q7：为什么重试不重新运行 agent/pre-step？

    因为 retry 属于同一个已接纳 step。重新 assembly 和 pre-step 可能重复注入上下文或产生不同用户 admission。DSH 重用同一 assembly，只在需要时让 compaction 改变 surface。

    Q8：流式输出中途取消，历史会不会丢？

    如果已有可见内容，会以 assistant/message 和 interrupted: true 落日志；没有可见内容则记录 attempt。下一请求能看到用户已经见过的前缀。

    Q9：工具失败会结束 Turn 吗？

    通常不会。Unknown、deny、throw、timeout 等会成为 error tool result，由模型决定下一步。工具流水线插件自身抛出且未归一化的错误可能结束当前 turn。

    Q10：多个工具如何并发？

    Parallel-safe calls 进入有界 rolling pool，exclusive calls 是 barrier。工具 body 可并发，但准入、结果 finalize 和日志 commit 保持模型顺序。

    Q11：为什么未执行的工具也要写错误结果？

    模型已输出 tool call。若日志只有 call 没有配对 result，恢复和 provider replay 可能非法。取消时用 ABORTED_BEFORE_DISPATCH 补齐配对。

    Q12：Session 为什么不用直接保存 messages？

    事件日志同时需要保存请求边界、失败 attempt、工具原始参数、压缩来源、持久化和回放事实。messages 只是日志 surface 的一个投影。

    Q13：Compaction 会删除原始历史吗？

    不会。它追加 replacement 事件，旧节点仍在 append-only log 中，只是不再出现在当前模型 surface。

    Q14：Compaction 会压缩 system prompt 和工具 schema 吗？

    不会。system head 被保护，工具 schema 属于 request header，不在可摘要的普通历史 span 中。它们本身太大时要减少 Prompt/工具集或换更大窗口。

    Q15：工具结果“压缩 50%”仍不够怎么办？

    先澄清：50% 是 spill 预览头尾预算分配，不是通用压缩率。完整结果应落盘并返回路径；历史结果再裁剪；整体历史再摘要。不可拆部分仍超窗时应显式失败，而不是无限重试。

    Q16：为什么 spill 失败时反而保留完整结果？

    因为返回不可读路径会让信息永久丢失。当前策略选择 fail-open 保留原始内容并告警；部署方应监控该告警并修复 storage/locator 配置。

    Q17：如何避免 spill notice 本身太大？

    缩短持久化路径或改用短 opaque handle；避免在 notice 里输出冗长 URI；给 notice 保留最低预算；必要时把读取工具改成 result_get(handle, offset, limit)。

    Q18：Token Meter 是精确 tokenizer 吗？

    不总是。部分路径使用启发式字符估算；provider usage 最权威。CJK 和大型 JSON Schema 可能被低估，应留足 headroom 并用真实流量校准。

    Q19：Profile、Bundle、Patch 怎么理解？

    Profile 是一个产品运行实例；Bundle 是可分发配置层；Patch 是对有 id 插件条目的替换、禁用或插入。最终运行树是有序 patch 的合成结果。

    Q20：怎样查看某台机器实际运行的插件树？

    使用 dsh --profile <name> --dump-config。不要只看仓库里的 base bundle，因为 profile、home 和命令行 patch 都可能覆盖它。

    Q21：如何增加一个模型 provider？

    实现 LLM adapter，注册到 ctx.llm；明确模型能力、context window、retry policy、错误归一、流协议和 system prompt update 能力。不要修改 AgentLoop。

    Q22：如何增加一个工具？

    用 defineTool() 声明 name、description、参数、输出、执行、并发分类和超时；注册到 ctx.tools；同时补工具 UI、错误语义、权限、单测和 recorded-session snapshot。

    Q23：Sandbox 是否足够在生产执行不可信代码？

    官方答案是否定的。它只是降低风险，不是唯一安全控制。仍需容器/VM、最小权限、网络隔离、短期凭据和外部审计。

    Q24：Subagent 会自动继承父 Agent 的所有限制吗？

    不能这样假设。In-process provider 有显式继承规则；外部 provider 有自己的工具与权限系统。每个 provider 都要审查 tool filter、sandbox、approval 和 recursion depth 支持。

    Q25：MCP 工具是否和原生工具一样安全？

    它们进入相同 ToolRuntime 策略链，但 server transport 和进程边界不同。特别是 stdio server 的创建、环境和进程树管理需要单独审查。

    Q26：为什么没有内置最大 Turn 步数？

    默认 Loop 把停止策略留给插件和部署。生产环境应增加 wall-clock、steps、tool calls、tokens 和 cost 多维预算。

    Q27：如何保证插件卸载不泄漏 listener 和工具？

    注册必须通过 ctx.effect() / ctx.on() 并返回 disposer；相关资源放进同一个 effect，确保按预期顺序逆向释放。

    Q28：为什么 Session format 版本管理这么严格？

    因为会话是用户已发布的数据。旧 runtime 如果不能完整理解新结构，就可能静默恢复出错误上下文。版本与相邻迁移避免“能 parse 但语义错误”。

    Q29：生产采用前最需要做什么？

    固定 commit/profile/patch；运行自己的回放测试；验证真实 provider 的超窗错误分类；压测大工具结果；审计 plugin、MCP、sandbox 和 credentials；在隔离环境运行。

    Q30：这个项目最值得其他 Agent 框架借鉴的设计是什么？

    不是插件数量，而是三项不变量：模型可见状态可从日志重建、注册都有生命周期 disposer、上下文替换保留来源关系。

    22. 结论与建议

    核心结论

    1. DeepSeek Harness 是完整 Agent Runtime，不是模型封装层。 置信度：高。
    2. Cordis 插件树和可逆 effect 是其架构中心；AgentLoop 只是其中一个可替换插件。 置信度：高。
    3. Session append-only log + surface replacement 是持久化、压缩和回放的共同基础。 置信度：高。
    4. 大工具结果采用 spill、历史裁剪和对话摘要三层处理，不存在无限 50% 压缩策略。 置信度：高。
    5. 安全能力属于风险降低而非完整隔离，当前 developer preview 不应未经外部控制直接承担高风险生产执行。 置信度：高。

    给 Agent 平台研发团队的行动建议

    1. 先把工具输出协议改成分页、过滤、句柄、按需读取；
    2. 让每次模型请求都能从 durable events 重建；
    3. 固化 tool pipeline 阶段，避免每个工具自行实现审批、timeout 和日志；
    4. 对 compaction 设置“必须实际缩小才允许重试”的不变量；
    5. 对每个 provider 归一 context overflow、rate limit、auth、timeout；
    6. 为 turn 增加总步数、时间、token、成本预算；
    7. 把 sandbox、network、credential 和 plugin trust 分开建模；
    8. 使用 recorded session replay 做 Agent 行为回归测试。
