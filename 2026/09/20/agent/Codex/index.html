    Codex Harness 核心流程分析

    项目定位

    Codex Harness 是 OpenAI 开发的生产级 Agent 运行时框架，Apache-2.0 协议开源，Rust 核心（codex-rs）+ TypeScript/Python SDK 双栈。它驱动 Codex App、CLI 和 VS Code 插件的底层执行框架，管理对话状态、工具调用、沙箱执行、流式输出和人工审批。核心理念：Harness 是 Agent 的操作系统——模型只是计算单元，Harness 负责记忆、工具、审批、沙箱、并发、可观测性。

    五部分核心组件

    Codex Harness 的核心组件可以分为 5 个部分：

    1. 上下文工程：Context Compaction（智能压缩长上下文，保留关键推理信息，非简单文本摘要）+ Retained Reasoning（保留中间推理痕迹供模型回溯）+ 结构化上下文管理替代杂乱长上下文拼接
    2. 工具/插件系统：MCP 集成（支持应用自有 MCP 服务，打通业务数据与操作）+ Skills 框架（可复用 Skill 包）+ Hooks 生命周期钩子 + model-provider 抽象层（支持任意 OpenAI 兼容端点）
    3. 状态持久化：Thread（完整对话会话，可 fork/resume）+ Turn（单轮交互）+ Item（Turn 内原子事件）+ thread-store/history 持久化存储
    4. 权限/安全模型：跨平台沙箱隔离（linux-sandbox/windows-sandbox-rs）+ execpolicy 执行策略 + 审批机制（Human-in-the-loop，高风险操作暂停等待确认）+ 三层审批策略（auto/manual/suggest）
    5. 可观测性和审计：app-server JSON-RPC 流式事件（实时看到 AI 在做什么）+ 中途打断能力 + codex agents 仪表盘（交互式 Agent 管理界面）

    一次完整请求流程

    用户通过 Codex App、CLI（codex exec）、SDK 或 app-server 发起请求。

    第一步：构建系统提示词。 组装系统指令、工具定义、技能描述等静态内容。静态内容放在 Prompt 前部，保证每轮都能命中 KV Cache，降低推理成本。

    第二步：Agent Loop 启动。 标准化 Agent 循环：接收用户输入 → 构造 Prompt → 发送给模型推理 → 拿到响应。响应往往不是最终答案，而是一次工具调用（如”运行这个 shell 命令并告诉我结果”）。

    第三步：工具调用执行。 Harness 执行工具调用：读写文件、运行 shell 命令、执行测试、调用 linter 和类型检查器等。工具调用结果追加到 Prompt 中，再次查询模型。这个循环可能重复几十次，直到模型产出给用户的最终消息。

    第四步：沙箱隔离。 工具执行在沙箱中进行。codex-rs 包含跨平台沙箱实现：linux-sandbox（内核级隔离）、windows-sandbox-rs（Windows 沙箱）。execpolicy 控制执行策略——哪些命令可以运行、哪些文件可以访问、哪些网络可以连接。

    第五步：人工审批。 高风险操作（如删除文件、执行危险命令、访问敏感数据）暂停并等待人类确认。审批策略分三档：auto（自动批准）、manual（必须人工确认）、suggest（建议但可自动执行）。v0.149.0 修复了 approval profile 在 resumed/forked 线程中静默回退的 bug。

    第六步：上下文压缩。 当上下文窗口填满时，Context Compaction 将历史编码为更小的表示。不是简单的文本摘要——保留关键推理信息（retained reasoning），让模型能回溯之前的思考过程。ARC-AGI-3 基准测试中，仅靠 retained reasoning + context compaction 两项优化，GPT-5.6 Sol 得分从 13.3% 跃升至 38.3%，输出 token 消耗降至原来的 1/6。

    第七步：流式事件推送。 app-server 通过 JSON-RPC 协议流式传输事件：用户消息、推理步骤、Shell 命令、文件编辑、工具调用结果。支持中途打断（turn/interrupt）。

    第八步：会话持久化。 Thread（完整对话）包含多个 Turn（单轮交互），每个 Turn 包含流式 Item 序列（原子事件）。Thread 支持 fork（分叉新路径）和 resume（恢复历史会话）。

    三层集成接口

    Codex Harness 提供三层接入方式，覆盖从脚本到产品的全场景：

    第一层：codex exec（CI 脚本 / 非交互任务）。 最轻量接入，一条 CLI 命令完成自动化任务。适合 CI/CD 流水线、批量脚本、后台一次性作业。执行完毕自动退出并返回结构化输出。

    第二层：Codex SDK（程序化 Agent 编排）。 TypeScript/Python 双接口，在应用代码中编程式启动、恢复、流式编排 Codex 任务。支持 thread/fork（分叉会话）、thread/resume（恢复历史会话）、turn/interrupt（中断当前轮次）。v0.149.0 新增 max/ultra 推理强度控制。

    第三层：Codex app-server（持久会话 + 流式事件 + 审批）。 为产品级接入设计的进程间通信层。基于 JSON-RPC 2.0，支持 stdio（默认）、Unix socket、WebSocket（实验性）三种传输方式。驱动 VS Code 插件和 Codex Desktop App 的运行时。

    关键设计决策

    1. Rust 核心 + TypeScript SDK 双栈。 codex-rs（约 120 个 crate）处理所有性能敏感路径（执行调度、沙箱、TUI 渲染、传输层）。TypeScript/Node.js 层保留为上层接口。资源占用和稳定性显著提升。

    2. Retained Reasoning + Context Compaction。 不是简单截断或摘要——保留中间推理痕迹，让模型能回溯之前的思考过程。这是 Harness 设计带来 3 倍效果提升的核心原因。

    3. app-server 协议自建。 OpenAI 评估后拒绝用 MCP 承担 app-server 角色——MCP 面向工具的”请求-响应”模型无法表达流式 diff、多步审批流和持久会话状态。因此自建了 app-server 协议。MCP 负责把外部工具接入 Codex，app-server 负责把客户端接入 Codex，两者分工共存。

    4. Thread/Turn/Item 三层会话模型。 Thread（完整对话）→ Turn（单轮交互）→ Item（原子事件）。支持 fork、resume、interrupt，构建完整的多轮 Agent 交互产品。

    5. 审批策略三档。 auto（自动批准所有操作）、manual（必须人工确认）、suggest（建议，不阻塞）。CI 场景用 auto，生产场景从 suggest 开始逐步过渡。

    6. 模型提供方抽象。 model-provider 模块支持任意 OpenAI 兼容端点。可以通过修改 base_url 接入 DeepSeek、Qwen、Kimi 等任意兼容模型。

    7. 开源边界清晰。 已开源：Codex CLI、SDK、app-server、codex exec、Skills、通用云环境。未开源：VS Code/JetBrains IDE 插件、Codex 网页版、云端托管产品、模型本身。

    摘要

    本文所说的“Codex Harness”是一个分析性称呼，源码项目的正式名称是 Codex CLI。它不是简单的终端聊天客户端，也不是一个单文件 ReAct 循环，而是一套完整的本地 coding-agent runtime：CLI/TUI/IDE/SDK 通过 app-server 控制线程和 turn；Core 将用户输入、项目指令、模型配置、工具目录和历史组装成 Responses API 请求；模型流式返回消息或工具调用；工具调用经 policy、hook、approval、sandbox、执行器和输出截断后回到历史；Rollout JSONL 保存可恢复事实；上下文压力由工具输出截断、本地/远端 compaction 和下一 turn 恢复机制共同治理。

    一次典型任务的主链可以概括为：

    CLI / TUI / exec / IDE / SDK

  -> TurnContext + StepContext

    核心结论：

    1. app-server 是统一控制面，Core Session 是运行时主体。 TUI 和 codex exec 都不是独立实现一套 Agent loop。
    2. 一个用户 turn 可以包含多次模型 sampling。 response.completed 不一定意味着 turn 结束；工具调用、end_turn=false 或 steer 都可能触发下一轮 sampling。
    3. 工具安全由多层共同实现。 ToolPolicy、execpolicy、approval、OS sandbox、网络代理和 hook 分别解决不同问题，任何单层都不是完整安全边界。
    4. Rollout 与模型 history 不是同一个东西。 Rollout 尽量保留原始事件；模型 history 会规范化、截断和压缩。
    5. 大结果先截断，长历史再 compact。 普通 provider 超窗通常结束当前 turn，并强制下一 turn 预压缩，而不是在同一次 sampling 中无限删历史重试。

    3. 总体架构：控制面、运行面和事实面

    可以把 Codex 拆成三层。

    3.1 控制面

    控制面负责：

    • 创建、恢复、fork 和归档 thread；
    • 开始、steer 和 interrupt turn；
    • 把审批问题发给客户端；
    • 把流式 item、usage 和状态通知客户端；
    • 接收动态工具结果和 MCP elicitation。

    主要实现是 app-server。协议形式接近 JSON-RPC，但源码明确省略标准的 "jsonrpc":"2.0" 字段。客户端必须先 initialize，再使用 thread/* 和 turn/* 方法。

    3.2 运行面

    运行面由 Core 驱动：

    • ThreadManager 管理 thread 创建和内存注册；
    • CodexThread 是客户端持有的线程句柄；
    • Session 保存一个 Agent 线程的运行时服务和状态；
    • TurnContext 固定一次 turn 的配置；
    • StepContext 固定一次 sampling 的工具、模型和环境视图；
    • run_turn() 驱动模型请求、工具调用和下一次 sampling。

    Session 源码明确规定“一个 Session 同时最多有一个 running task”，并通过 active_turn、input_queue 和 cancellation 管理并发输入。Session

    3.3 事实面

    事实面有两种不同视图：

    • Rollout JSONL：用于持久化、审计、resume 和 fork，尽量保留原始 ResponseItem 与状态事件；
    • ContextManager history：下一次发给模型的规范化视图，执行配对修复、模态过滤、工具输出截断和 compaction replacement。

    这个分离非常重要：模型不需要看到所有运行日志，但恢复过程需要知道比“messages 数组”更多的事实。

    4. 启动与产品入口

    4.1 CLI 根入口

    codex-rs/cli/src/main.rs 中的 MultitoolCli 定义了交互 TUI 和子命令。无子命令时进入交互式 CLI；主要子命令包括：

    • exec：非交互运行；
    • review：非交互代码审查；
    • app-server：启动控制面；
    • mcp：管理 MCP server；
    • sandbox：在 Codex sandbox 内执行命令；
    • resume / fork / queue；
    • cloud；
    • doctor、features、debug 等。

    源码：MultitoolCli 与 Subcommand

    4.2 TUI 不是另一个 Agent loop

    TUI 的职责是：

    • 呈现 thread 和 turn；
    • 发送 turn/start、turn/steer 和 turn/interrupt；
    • 显示流式 item；
    • 处理审批、MCP elicitation、request_user_input；
    • 在 embedded app-server、本地 daemon 和远端 transport 间选择。

    没有活动 turn 时，用户输入发起 turn_start；已有活动 turn 时输入进入 turn_steer。真正的模型/工具循环仍在 Core。

    4.3 codex exec

    codex exec 是面向脚本、CI 和一次性任务的 headless 客户端。它同样通过 in-process app-server 发 TurnStart 并消费通知，而不是直接调用模型。

    与 TUI 的关键差异：

    • 默认 approval 为 never；
    • 不能真正进行交互审批；
    • request_user_input 通常被拒绝；
    • stdout 只输出最终文本或严格 JSONL，其余诊断走 stderr；
    • 支持 schema、ephemeral、resume、fork 和 review。

    4.4 App-server 的意义

    app-server 将 UI/SDK 与 Core 解耦。TUI、exec、Python SDK、IDE 都可以复用：

    thread/start
thread/resume
thread/fork
turn/start
turn/steer
turn/interrupt

    这比让每个客户端直接链接一套内部 Agent 类型更稳定，也便于将 embedded runtime 替换为 daemon 或远端 transport。

    5. 核心对象与数据流

    5.1 ThreadManager

    ThreadManager 负责：

    • 创建/恢复/fork thread；
    • 维护 ThreadId -> Arc<CodexThread> 注册表；
    • 加载 Rollout；
    • 创建 Session；
    • 等待首个 SessionConfigured 后再向调用方发布 thread。

    这是一道发布边界：客户端拿到 CodexThread 时，核心 Session 已完成初始配置。

    5.2 CodexThread

    CodexThread 是外部控制 Core 的句柄，关键能力包括：

    • submit()：提交普通 Op；
    • start_or_steer_turn()；
    • steer_turn()；
    • next_event()；
    • recover_turn_if_idle()。

    它不承载完整业务状态，真正状态在 Session。

    5.3 Session

    Session 持有：

    • thread id 和事件 channel；
    • SessionState；
    • active_turn；
    • input queue；
    • model client、rollout、tools、MCP、auth、telemetry 等服务；
    • sandbox/permission profile；
    • 动态工具、multi-agent 版本和附件服务。

    5.4 Op、Submission 与 EventMsg

    Core 输入是 Submission：

    submission id
+ Op
+ trace context
+ turn lineage
+ residency guard

    Op 包含 TurnInput、Interrupt、审批响应、动态工具响应、Compact、Review、Shutdown 等。submission_loop 串行消费控制操作，避免多个控制命令无序修改同一个 active turn。

    Core 输出是 Event { id, msg: EventMsg }。客户端通过事件看到 turn、item、approval、usage、warning 和 error。

    5.5 Codex 中没有单一 Turn 运行时 struct

    源码容易误读的一点是：Core 的运行态并非一个包含所有内容的 Turn struct，而是由以下对象组合：

    • TurnContext：一次 turn 的固定配置和元数据；
    • StepContext：一次 sampling 捕获的工具和环境；
    • ActiveTurn：当前任务、pending input 和状态；
    • RunningTask / TurnState；
    • app-server 协议中的 Turn：面向客户端的投影。

    6. 从用户输入到一次 Turn

    6.1 输入路由

    app-server 的 turn_start_inner 将协议层 UserInput 转为 Core TurnInputRequest。SessionIo::submit_turn_input 把请求包装成 Op::TurnInput，放入容量受限的 async channel。

    submission_loop 串行路由后，turn_input::start_or_steer 在 active-turn 锁下决定：

    • Started：当前 idle，创建 RegularTask；
    • Steered：已有活动 turn，写入 pending input；
    • NotSubmitted：状态不接受。

    并发提交时，最多一个请求真正启动新 turn，其余可进入 steer，而不是同时运行两个 turn。

    6.2 run_turn() 主循环

    run_turn() 的简化流程：

    运行 TurnStart hooks
记录用户输入与注入上下文
准备 shell snapshot / connector selection
创建 turn-scoped ModelClientSession
loop:
  领取可进入下一 step 的 pending input
  运行 SteeredUserInput hooks
  捕获 StepContext
  更新 world state / instructions / skills
  clone history -> for_prompt
  run_sampling_request
  处理工具与 assistant output
  检查 pending input 与 token pressure

  如果 model/tool/steer 需要 follow-up -> continue

    关键代码显示：同一个 ModelClientSession 在一个 turn 的 retry/sampling 间复用，以保留 WebSocket 与 sticky routing 状态。run_turn 主循环

    6.3 StepContext 是一次请求视图

    每轮 sampling 前重新捕获 StepContext，确保以下内容来自同一个一致快照：

    • 模型与 reasoning settings；
    • 当前工具目录；
    • MCP binding；
    • sandbox/permission；
    • environment；
    • skills 和 project instructions。

    如果 pending steer 引入新的 plugin/MCP 依赖，系统重新解析 required servers 和 plugins，再捕获新的 StepContext。

    下一次模型请求主要由以下部分组成：

    • base instructions；
    • global/thread/project instructions；
    • history.for_prompt()；
    • 当前工具 specs；
    • output schema；
    • reasoning、service tier 等请求配置。

    • 保证 function call 与 output 的配对；

    7.1 请求协议

    ModelClientSession::stream() 优先使用 Responses WebSocket；必要时回退 HTTP SSE。HTTP 路径 POST /responses，要求 text/event-stream。

    请求通常包含：

    • model；
    • input history；
    • instructions；
    • tools；
    • tool_choice=auto；
    • stream=true；
    • reasoning 与 output schema 等扩展。

    7.2 流事件

    Core 消费的主要事件：

    • Created；
    • OutputItemAdded；
    • text/reasoning/tool argument delta；
    • OutputItemDone；
    • token usage、rate limits、model metadata；
    • Completed。

    如果 stream 在 response.completed 前关闭，Core 将其视为错误，而不是把半截结果当成正常完成。流关闭检查

    7.3 response.completed 不等于用户 Turn 结束

    收到 Completed 时，Core 记录 usage 和 response id。以下情况会继续下一次 sampling：

    • 本次输出包含需要执行的工具；
    • provider 返回 end_turn=false；
    • pending steer/input 已到达；
    • hook 产生 continuation；
    • compaction 后需要继续；
    • mailbox/multi-agent 通信要求 follow-up。

    1. handle_output_item_done() 持久化模型输出；

    3. ToolCallRuntime 判断可否并发；
    4. 工具 future 放入 FuturesOrdered；
    5. 执行可以并发，但结果按模型顺序 drain；
    6. tool output 写入 history；
    7. needs_follow_up=true；
    8. 外层 turn loop 用新 history 发下一次模型请求。

    源码使用 FuturesOrdered 保持提交到 history 的顺序。工具 drain

    8.1 ToolSpec 与 ToolExecutor

    工具不是只有一份 JSON Schema。ToolExecutor 将以下内容绑定：

    • 工具名称与 namespace；
    • ToolSpec；
    • exposure；
    • 是否允许并行；
    • handler/runtime。

    ToolSpec 支持 Function、Namespace、ToolSearch、WebSearch 和 Freeform。

    8.2 工具来源

    Step 的工具目录可来自：

    • extension/plugin；
    • app-server host 注入的 dynamic tools；
    • hosted tool；

    8.3 注册与冲突

    • ToolPolicy 不允许的工具不会注册；
    • 内建可信工具重复注册是错误；
    • 外部工具同名时先注册者生效，并记录 collision；
    • 外部工具不能占用默认 namespace 的 exec_command / shell_command；
    • exposure 决定直接可见、deferred、hidden 等状态。

    9. 工具执行流水线

    9.1 从模型 item 到 handler

    统一链路：

    ResponseItem
 -> ToolRouter::build_tool_call
 -> ToolCallRuntime parallel/exclusive gate
 -> ToolRegistry::dispatch_any_with_state
 -> PreToolUse hooks
 -> concrete handler
 -> PostToolUse hooks
 -> ToolOutput::to_response_item
 -> ContextManager history

    9.2 PreToolUse 与 PostToolUse

    PreToolUse hook 在执行前运行，可以：

    • block；
    • 修改允许修改的输入；
    • continue。

    PostToolUse hook 在工具已经执行后运行。它可以：

    • 附加上下文；
    • 把结果反馈替换成另一段模型可见文本；
    • block 结果。

    但它不能回滚已经发生的文件、网络或进程副作用。源码对此有明确注释。PostToolUse 语义

    9.3 错误语义

    工具错误分为：

    • RespondToModel：转成普通失败 tool output，让模型继续；
    • Fatal：终止当前流程；
    • sandbox/approval 拒绝；
    • timeout/cancellation；
    • handler 执行失败。

    Unknown tool 通常成为模型可见错误，而 payload kind 与已注册工具不匹配可视为 fatal protocol error。

    9.4 并发语义

    ToolCallRuntime 使用读写锁表达并发：

    • 支持 parallel 的工具取得共享许可；
    • 非 parallel 工具取得独占许可；
    • future 可并发运行；
    • 结果由 FuturesOrdered 按模型 item 顺序写回。

    工具的并行声明只说明单次调用可以并行，不自动解决两个调用对同一个文件、进程或外部资源的业务冲突。

    10. Shell、Unified Exec 与 Apply Patch

    10.1 Unified Exec

    exec_command 的主要步骤：

    1. 解析参数；
    2. 选择 cwd、environment 与 shell；
    3. 校验 TTY、timeout 和 additional permissions；
    4. 识别伪装成 shell 命令的 apply_patch；
    5. 通过 execpolicy 判定；
    6. 进入 ToolOrchestrator；
    7. 选择 sandbox；
    8. 启动本地 PTY 或远端 exec-server；
    9. 返回输出或 session id。

    Unified Exec 开启时支持可恢复进程与 write_stdin；关闭时只暴露 one-shot exec_command。

    10.2 后台进程

    一次 exec 初始等待通常受最小/最大值约束。超过等待并不一定杀进程，而可能返回 session id，让 Agent 后续用 write_stdin 读取。只有 one-shot 明确 timeout 时才确认终止。

    进程管理器限制保留数量，并优先清理较旧、已退出的进程。Turn cancellation 会中止当前 dispatch，但已经被进程管理器接管的后台终端可能继续存在，需要显式清理。

    10.3 Apply Patch

    apply_patch 是 freeform grammar tool，不是普通 shell 文本。它会：

    • parse patch；
    • 解析目标 environment；
    • 对所有源/目标路径做 sandbox 检查；
    • 通过 ToolOrchestrator 执行。

    重要限制：apply patch 不是事务性的。如果中间失败，前面已经写入的 delta 可能保留。Harness 不保证自动回滚，调用方应检查工作树和 diff。

    11. Approval、Permission 与 Execpolicy

    11.1 Approval Policy

    AskForApproval 包含：

    模式 含义
    UnlessTrusted 用于不可信项目；除非 execpolicy 明确允许，否则需要审批
    OnRequest 默认；模型/策略决定何时申请
    Granular 分别控制 sandbox、rules、skill、permission、MCP elicitation
    Never 永不向用户提问；需要审批的动作直接失败，而不是全部放行

    源码：AskForApproval

    11.2 Execpolicy

    Execpolicy 将命令归为：

    • Forbidden；
    • Prompt；
    • Allow。

    只有所有相关命令段都被显式规则允许，才可能形成 bypass sandbox 的结论。危险命令识别本身含启发式成分，不应作为唯一安全控制。

    11.3 Permission Request

    模型可通过 request_permissions 申请附加路径或网络权限。系统会：

    • 规范化相对路径；
    • 将客户端批准结果与原请求求交集；
    • 防止客户端响应意外授予模型未申请的更大权限；
    • 将授权限制为 turn 或 session 生命周期。

    Never 或 Granular 禁止相应类别时，不弹窗并返回空授权。

    11.4 Approval 的解析顺序

    审批可以由多种 reviewer 决定：

    permission hook
 -> Guardian/auto review
 -> human client

    最终仍需由 ToolOrchestrator 把审批结论与 sandbox policy 结合，而不是把“已批准”直接等价成“无条件在宿主执行”。

    12. Sandbox 与网络安全

    12.1 ToolOrchestrator

    ToolOrchestrator 集中实现：

    审批 requirement
 -> 选择第一轮 sandbox
 -> 执行
 -> 若确定是 sandbox denial
 -> 检查是否允许升级
 -> 再次审批/Guardian review
 -> 第二次执行

    它不会对任意错误都“去沙箱重试”。只有识别为 sandbox denial，并同时满足 approval 与 policy 条件，才进入升级路径。ToolOrchestrator

    12.2 SandboxPolicy

    协议层常见模式：

    • read-only；
    • workspace-write；
    • danger-full-access。

    danger-full-access 明确表示无执行限制，应谨慎使用。read-only 默认不开放网络。SandboxPolicy

    12.3 Linux

    当前主要路径使用 bubblewrap 建立文件系统 namespace，并在内层使用 no_new_privs 与 seccomp。Legacy Landlock 是兼容路径；无法表达某些 deny-read 政策时会拒绝，而不是静默降级。

    12.4 macOS

    macOS 固定调用 /usr/bin/sandbox-exec，使用 deny-default Seatbelt profile，动态加入读写根、只读 carveout、网络代理端口与 socket 规则。固定绝对路径可减少 PATH 劫持。

    12.5 Windows

    Windows 使用 restricted token、ACL、私有 desktop、Job Object，并可用 WFP 约束网络。若某 backend 无法实现请求的 deny-read 语义，应 fail closed。

    12.6 网络

    Managed network 通常让 sandbox 进程只能访问本地代理，再由代理执行域名策略。如果代理不可用，受管网络路径应失败。显式 require_escalated 可能绕过该代理，因此必须依赖审批和权限政策。

    12.7 哪些是保证，哪些只是风险降低

    在正确启用并由支持平台实现时，下列可作为条件性保证：

    • OS sandbox enforcement；
    • permission 结果不超过原请求；
    • 不支持要求时 fail closed；
    • reserved tool name 防覆盖。

    下列只能视为风险降低：

    • 命令 Read/Search 分类；
    • 危险命令启发式；
    • sandbox-denial 错误识别；
    • 按变量名过滤 secret；
    • 模型主动决定何时申请权限；
    • 外部 MCP server 的可信度。

    13. 工具输出截断

    13.1 为什么先截断当前结果

    一个 shell 命令可能返回数十 MB 内容。如果先把完整结果塞进 history，再等整个 thread 接近窗口时 compact，可能单次请求已经无法构建。因此 Codex 在结果进入 live model history 时就执行截断。

    13.2 Rollout 原文与模型结果分离

    record_annotated_items() 的注释明确说明：工具输出截断只作用于 live history，原始 Rollout payload 保留。Resume 时根据保存的 truncation metadata 重新得到一致的模型视图。History 截断

    13.3 截断算法

    文本使用中间截断，保留前后信息。formatted_truncate_text() 会增加：

    • 原始估算 token 数；
    • 总行数；
    • 截断后的内容。

    Function output 可按 byte 或 token budget 处理；序列化还增加 20% allowance。Content items 中：

    • 文本受预算；
    • 图片保留；
    • 音频按估算 token 成本选择；
    • 加密内容保留；
    • 省略项加 marker。

    源码：output-truncation

    13.4 与 DeepSeek Harness Spill 的差异

    Codex 当前通用路径更偏向“在模型 history 中截断并在 Rollout 中保留原始 payload”，不是统一把完整结果写成模型可读文件并返回句柄。模型能否重新读取原始内容取决于原工具、文件系统或外部服务是否支持按需查询。

    因此，设计自定义 Codex 工具时，仍建议工具本身支持：

    • 分页；
    • 字段选择；
    • offset/limit；
    • 结果 handle；
    • 可搜索制品。

    Rollout 保存原文不等于模型自动拥有读取 Rollout 的工具。

    14. Context Window 与 Compaction

    14.1 三种机制必须区分

    机制 处理对象 时机 是否调用模型
    Tool output truncation 单个当前/历史工具结果 写入 model history 时 否
    Local/remote compaction 整段历史 turn 前、中、后或用户手动触发 通常是
    Provider 超窗恢复 真实 API 超窗错误 sampling 失败后 当前 turn 通常失败，推动下一 turn 预压缩

    14.2 Token pressure

    系统结合：

    • provider 报告的 usage；
    • 本地新增尾部估算；
    • auto-compact threshold；
    • effective context hard cap

    判断是否需要 rollover/compact。Compaction 可以在 pre-turn、mid-turn 和 post-turn 执行。

    14.3 Local Compaction

    本地 compaction 的步骤：

    1. 使用内置 SUMMARIZATION_PROMPT 或自定义 compact prompt；
    2. 复制当前 history；
    3. 加入 compaction 请求；
    4. 调用 Responses API 生成 summary；
    5. 若 compaction 请求本身超窗，从最老 history item 开始逐项删除并重试；
    6. 收集真实 user messages；
    7. 最近用户文本最多保留约 20k token；
    8. 加入 SUMMARY_PREFIX + summary；
    9. 重新注入当前 canonical context；
    10. 写入 compacted replacement history 和 window metadata；
    11. 重新计算 usage。

    源码：Local compaction、replacement history

    14.4 Remote Compaction V2

    Remote V2 不是普通文本 summary 请求，而是发送 compaction trigger 并接收 opaque compaction item。提交前会改写连续超大工具输出，保持 function call/output 配对，并按历史与图片预算构建 replacement history。

    它适合由服务端掌握更强压缩能力的 provider，但开源 Harness 仍负责 checkpoint、window、resume 和本地后缀。

    14.5 Provider 真实超窗

    普通 sampling 收到 ContextWindowExceeded 时，Codex 不会简单在同一请求中无限删除历史重试。主要行为是：

    • 将 active token usage 标记为已填满窗口；
    • 当前 turn 返回错误；
    • 下一 turn 的 pre-compact 判断必然触发。

    只有部分 Guardian 特殊路径会在同一 turn compact 后再试一次。

    14.6 如果工具结果压缩后仍超过窗口

    正确处理顺序：

    单个结果
 -> 先按工具/模型预算截断
 -> 工具设计支持分页、过滤和结果句柄

整体 history 仍大
 -> local 或 remote compaction
 -> 保留近期用户目标和 canonical context

compaction 请求本身超窗
 -> 删除最老 history item 后重试 compaction

普通 sampling 仍被 provider 判定超窗
 -> 当前 turn 失败并标记 full
 -> 下一 turn 预压缩

固定成本仍过大
 -> 减少 instructions、tools、MCP catalog、skills
 -> 或更换更大 context 的模型

    不应把“Rollout 中有原文”误解成“模型仍能访问完整结果”；也不应让 provider 超窗进入无界重试。

    15. Rollout JSONL：持久化事实源

    15.1 RolloutItem

    JSONL 每行是带 timestamp/ordinal 的 RolloutItem。主要类型：

    • SessionMeta；
    • 原始 ResponseItem；
    • Compacted；
    • TurnContext；
    • TokenUsageRecord；
    • WorldState；
    • selected EventMsg；
    • inter-agent communication；
    • retained context。

    不是所有实时 delta 都持久化。原始流 delta、部分 warning/error 和临时 begin event 可被持久化策略过滤。

    15.2 写入语义

    新 session 延迟创建 rollout 文件。第一次 persist/flush 先写 SessionMeta，然后按 ordinal 顺序追加 JSONL 并 flush。若写失败，未写后缀保留，重开后继续尝试。

    15.3 Resume

    Resume 的关键步骤：

    1. 逐行读取；
    2. 坏 JSON 或未知记录可计数后跳过；
    3. 找最新可作为重建边界的 compaction；
    4. 使用 replacement history；
    5. 重放其后的 ResponseItem、rollback、world state 与 inter-agent message；
    6. 恢复最后 turn、模型设置和 context window lineage。

    源码：Rollout reconstruction、history replay

    15.4 Fork

    Legacy 模式可复制历史；Paginated 模式可通过 history base 引用祖先前缀。中途 fork 可以截到某个用户 turn 边界，并为开放的父 turn 添加与 interrupt 等价的结束标记。

    15.5 Rollout 不等于完整审计平台

    Rollout 的首要目的是 Codex session 恢复和历史重建。持久化策略会过滤事件，且可能包含敏感命令和模型内容。生产审计仍应单独设计：

    • 访问控制；
    • 保留周期；
    • 脱敏；
    • 不可抵赖日志；
    • 合规导出。

    18. MCP：发现、Binding 与调用

    18.1 Transport

    支持：

    • stdio；
    • streamable HTTP；
    • OAuth、Bearer、ChatGPT 等认证路径。

    常见配置位于 ~/.codex/config.toml；可信项目可以提供 .codex/config.toml。

    18.2 工具发现

    MCP 工具发现支持并发和分页，并设置最大页数、最大工具数和总超时。发现后应用：

    • enabled/disabled tools；
    • permission；
    • exposure；
    • 名称清洗和冲突处理。

    模型可见名称通常是 mcp__<server>__<tool>，并受最大长度限制。

    18.3 Immutable Binding

    每个 step 捕获不可变 McpBinding，固定：

    • client；
    • catalog revision；
    • permission；
    • timeout。

    如果 catalog 刷新后旧 binding 已陈旧，调用应拒绝，避免“模型看到 A 工具定义，但执行时实际变成 B”这种 TOCTOU。

    18.4 MCP 安全边界

    MCP 调用会进入 Codex ToolRegistry 与 approval 流程，但 MCP server 本身的内部行为不受本机 shell sandbox 自动约束。尤其是远端 MCP，它的副作用发生在服务端。需要分别治理：

    • transport 信任；
    • server 凭据；
    • per-tool approval；
    • tool allowlist；
    • 服务端审计和租户隔离。

    19. Hooks 与 Dynamic Tools

    19.1 Hooks

    Codex 支持多个生命周期 hook，如 SessionStart、TurnStart、PreToolUse、PostToolUse、Stop、Interrupt 等。Hook 可执行 command 或 MCP tool；配置中出现 Prompt/Agent 类型并不代表当前实现会执行它们。

    普通 hook 需要 trusted hash 才执行；managed/builtin hook 可自动可信；企业还可限制只允许运行 managed hooks。

    19.2 Hook timeout

    普通 hook 的默认超时较长；SessionEnd/Interrupt 等关闭路径使用更短上限，避免退出被无限挂住。

    19.3 Dynamic Tools

    IDE/host 可在 thread/start.dynamicTools 注入动态工具。模型调用后：

    1. app-server 向客户端反向发送 tool call；
    2. 客户端执行；
    3. 客户端回传文本、图片或音频结果；
    4. Core 将结果继续作为模型 history。

    这使 Codex 可以接入 IDE 内部能力，而无需所有工具都编译进 CLI。

    20.1 两套版本

    20.3 子 Agent 继承

    子 Agent 可继承：

    • provider/model；
    • approval；
    • sandbox；
    • cwd；
    • 指令快照；
    • role overlay。

    继承必须在 child_config 中显式定义。不要假设父级所有动态工具、MCP 认证或临时状态都会自动、等价地传给子级。

    20.4 Fork 与 Spawn 的区别

    • Spawn：更像新 thread，根据 child config 构造新的执行上下文；
    • Fork：共享/引用父 history 的一段前缀，适合保留上下文；
    • 共享历史有利于上下文连续性，但也扩大敏感信息传播范围。

    21. Interrupt、Steer、Retry 与完成语义

    21.1 Steer

    Steer 不创建一个新的并行 turn，而是把输入加入当前 TurnState.pending_input。下一轮 sampling 前，turn loop 领取 pending input，运行 SteeredUserInput hook，并重新捕获 StepContext。

    这允许用户在模型运行时补充方向，又避免两个 turn 同时修改一个 Session。

    21.2 Interrupt

    客户端调用 turn/interrupt，Core 收到 Op::Interrupt：

    1. cancellation token 触发；
    2. 给任务短暂宽限收敛；
    3. 必要时 abort Tokio task；
    4. 执行 abort hooks；
    5. 写中断 marker；
    6. 发 TurnAborted。

    Interrupt 与普通模型错误不同。普通错误可以发 Error，最终仍以带 error 的 TurnComplete 收口。

    21.3 网络与流重试

    Responses stream error 有受控重试：

    • 最大次数；
    • backoff / Retry-After；
    • 断网重连；
    • WebSocket 到 HTTP fallback。

    内部 recover_turn_if_idle() 可复用原 turn id 并标记 retry trigger，但不是一个普遍公开的 turn/retry RPC。

    21.4 完成

    只有以下条件都不再要求继续时，turn 才真正完成：

    • 没有 tool follow-up；
    • 没有 pending steer/mail；
    • provider 没要求继续；
    • hook 没注入 continuation；
    • 没有 compaction rollover；
    • 当前 task 正常收敛。

    25.1 客户端与 Core 解耦

    25.2 Step 快照降低竞态

    25.4 Rollout 与 history 分离

    25.5 跨平台安全实现较完整

    26. 局限与风险

    26.1 复杂度高

    Core、app-server、protocol、rollout、tools、sandbox、config 和扩展拥有大量交叉类型。源码学习门槛高，客户端版本和服务端协议也在快速演进。

    26.2 两套 SDK 能力不一致

    Python app-server SDK 与 TypeScript exec SDK 的 thread、审批、动态工具和并发能力不同。

    26.3 工具完整原文不一定可被模型重新读取

    Rollout 保存原始 payload 主要服务恢复与审计；通用 output truncation 没有统一返回可读句柄。大数据工具仍需自己设计分页/制品协议。

    26.4 PostToolUse 不能回滚

    PostToolUse block 只阻止结果进入模型，不能撤销工具已完成副作用。安全决策尽量放到 PreToolUse、approval 和 sandbox。

    26.5 Apply Patch 非事务性

    部分 patch 可能已写入。出错后必须检查 diff，不能假设工作树自动恢复。

    26.6 MCP 与 Dynamic Tool 扩大信任面

    本地 shell sandbox 不会自动约束远端服务端行为。Host callback 也需要自身授权和审计。

    26.7 Compaction 有信息损失

    源码在 compact 完成后会提示：长线程和多次压缩可能降低模型准确率，建议保持 thread 小而聚焦。摘要不是无损存储。

    26.8 配置迁移面较大

    Profile v2、legacy managed config、features 和 SDK protocol 共存，部署需要固定版本、配置 schema 和升级测试。

    12–22 分钟：Session 与 Turn Loop

    讲稿

    Codex 的运行态不是一个巨大的 Agent struct。ThreadManager 管理 thread，CodexThread 是句柄，Session 是真正的 Agent 线程状态。

    Session 同时最多一个 running task。用户在运行中继续输入，不会启动第二个并行 turn，而是进入 steer/pending input。

    一次新输入先被封装成 Submission 和 Op::TurnInput。submission loop 串行处理控制操作。在 active-turn 锁下，系统决定 Started 或 Steered。

    进入 run_turn() 后，先运行 hooks、记录输入、准备环境。然后进入 loop：领取 pending input、刷新 instructions 和 MCP、捕获 StepContext、从 history 构造 prompt、发 Responses 请求、处理工具，再判断是否继续。

    这里最值得学习的是 StepContext。模型、工具、MCP binding、sandbox 和 environment 在一次 sampling 前固定。这样模型看到的工具 schema 和真正执行的 handler 属于同一个 revision。

    同一个 turn 可以有很多 sampling。模型先请求 shell，执行后再 sampling；用户中途 steer，再 sampling；上下文达到阈值，compact 后再 sampling。只有没有 follow-up 时 turn 才结束。

    22–32 分钟：Responses Stream 与工具循环

    讲稿

    模型调用优先走 Responses WebSocket，必要时回退 HTTP SSE。流中会出现 item added、delta、item done、usage 和 completed。

    response.completed 不是用户 turn 的结束信号。它只表示这一次 upstream response 完成。如果模型输出工具调用，或者 end_turn=false，或者用户 steer 已到达，外层 loop 继续下一次 sampling。

    工具 item 完成后，ToolRouter 构造 invocation，ToolCallRuntime 处理并发，ToolRegistry 找 handler，结果放进 FuturesOrdered。工具可以并行执行，但写回 history 仍按模型顺序。

    工具目录来自多个源：Core、MCP、extension、host dynamic tools 和 multi-agent control。ToolPolicy 先做能力上限，exposure 决定模型可见方式，reserved name 防止外部工具覆盖 exec_command。

    PreToolUse 在副作用前，适合阻断或修改输入。PostToolUse 在工具执行后，只能影响结果和后续上下文，不能撤销副作用。

    32–42 分钟：Approval、Sandbox 与执行

    讲稿

    Codex 的工具安全不能用一个开关解释。至少有五层：ToolPolicy、execpolicy、approval、OS sandbox、network policy。

    Approval 有 OnRequest、Never、Granular 等模式。Never 不是“全允许”，而是“永远不问，需要批准的动作失败”。这对 headless exec 很重要。

    ToolOrchestrator 先判断 approval requirement，再选择 sandbox 执行。如果失败被确认是 sandbox denial，且 policy 允许，系统才可能再次审批并升级执行。普通命令失败不会自动裸跑。

    Linux 使用 bubblewrap 加 seccomp；macOS 使用 Seatbelt；Windows 使用 restricted token、ACL、Job Object 和 WFP。平台不能实现 requested deny-read 时，关键路径选择 fail closed。

    网络通常通过本地代理做域名策略。但远端 MCP 的副作用发生在服务端，不受本地 shell sandbox 约束。

    最后提醒 apply_patch 非事务性。失败时可能有部分修改，需要检查 diff。

    42–50 分钟：Rollout、截断与 Compaction

    讲稿

    Codex 有两个历史：Rollout 和 model history。

    Rollout JSONL 保存 SessionMeta、原始 ResponseItem、Compacted、TurnContext、usage 和 world state，用于 resume/fork。Model history 由 ContextManager 构建，会修复 call/output 配对、过滤不支持模态、截断工具输出并应用 compact replacement。

    工具输出在进入 live history 时按 byte/token budget 中间截断；原始 payload 仍留在 Rollout。注意：留在 Rollout 不代表模型有工具重新读取原文。

    当整个上下文接近阈值时，Codex compact。Local compaction 调模型生成 summary，保留近期用户目标，重新注入 canonical context，并替换 history。Compaction 请求本身超窗时，会删除最老 item 再试。

    普通 sampling 被 provider 判定超窗时，当前 turn 通常结束并把 usage 标成满窗，确保下一 turn 先 compact；不是当前请求无限删除历史重试。

    50–55 分钟：MCP、Skills 与 Multi-agent

    讲稿

    MCP 支持 stdio 和 streamable HTTP。工具发现后做 allow/deny、权限、exposure 和名称去重。每个 StepContext 捕获 immutable binding，catalog 刷新后陈旧调用会被拒绝，避免 schema 和执行错位。

    AGENTS.md 从项目根到 cwd 逐级加载，override 优先，默认总预算 32 KiB；不可信项目不读项目指令。Skills 只识别 SKILL.md，并有扫描和 prompt 预算。

    Multi-agent 默认有 V1，V2 在该版本默认关闭。子 Agent 可继承模型、sandbox、approval、cwd 和指令，但继承由 child config 明确定义，不要猜测。

    55–60 分钟：总结与问答

    讲稿

    今天带走六个结论。

    第一，Codex CLI 的核心不是 TUI，而是 app-server 加 Core Session。

    第二，一个 turn 可以包含多次 Responses sampling；response.completed 不是最终 turn complete。

    第三，工具执行必须经过 policy、hook、approval、sandbox 和 runtime，不能只依赖模型自律。

    第四，Rollout 是恢复事实，model history 是受预算约束的投影。

    第五，大结果先截断，长历史再 compact；固定 Prompt 和工具目录太大时只能减少固定成本。

    第六，二次开发优先接 app-server，并把工具的权限、截断、取消和持久化一起设计。

    如果团队准备落地，我建议做四个 POC：

    1. app-server thread/turn 客户端；
    2. 高风险工具审批与 sandbox；
    3. 大输出、compact、resume 一致性；
    4. MCP catalog 热更新和 stale binding。

    30. FAQ

    Q1：Codex Harness 是官方项目名吗？

    不是。官方开源项目名是 Codex CLI。本文用 Harness 指围绕模型的运行、工具、安全、上下文和持久化系统。

    Q2：Codex CLI 只是一个终端 UI 吗？

    不是。TUI 只是客户端；仓库还包含 app-server、Core、沙箱、Rollout、MCP、SDK 和多 Agent 能力。

    Q3：TUI 和 codex exec 是否各自实现 Agent loop？

    不是。二者都通过 app-server 控制 Core thread/turn；exec 是 headless client。

    Q4：Codex 的核心 Agent 对象是什么？

    没有一个包办一切的单体对象。ThreadManager 管理线程，CodexThread 是句柄，Session 保存运行态，TurnContext/StepContext 固定一次 turn/sampling 视图。

    Q5：Turn 与模型 Response 是一一对应吗？

    不是。一个 turn 可包含多次 response：工具执行、steer、hook continuation、compaction 都可能触发下一次 sampling。

    Q6：response.completed 是否表示 TurnComplete？

    不一定。它只表示一次上游 response 完成。Core 还要检查工具、pending input、end_turn 和 hooks。

    Q7：用户运行中继续输入会怎样？

    通常进入 steer/pending input，不启动第二个并行 turn。下一次 sampling 前被领取并重新捕获 StepContext。

    Q8：为什么一次 Session 只允许一个 running task？

    为了保证 thread 状态、Rollout 和 turn 生命周期一致。Turn 内仍可并发执行声明为 parallel-safe 的工具。

    Q9：工具执行结果为什么还要按顺序写回？

    模型输出的 tool calls 有确定顺序。即使 body 并发，使用 FuturesOrdered 写回可保持 replay 和下一次模型输入稳定。

    Q10：Codex 有独立的 read/grep 工具吗？

    固定 commit 的内建 shell family 主要是 exec_command 和 write_stdin；读取/搜索通常通过 shell 命令。MCP 或扩展可提供独立工具。

    Q11：ToolPolicy 和 Approval 有什么区别？

    ToolPolicy 是 Session 能力上限，决定工具能否存在；Approval 决定某次具体调用是否需要用户或 reviewer 授权。

    Q12：approval_policy = never 是否表示全部允许？

    不是。它表示永不询问用户；需要审批的动作直接失败并返回模型。

    Q13：PostToolUse hook 能否阻止副作用？

    不能。它运行时工具已经完成，只能阻止/替换结果。副作用控制应放在 PreToolUse、approval、sandbox 和工具内部。

    Q14：Sandbox denial 后是否总会裸跑重试？

    不会。只有错误被识别为 sandbox denial，并且工具、approval 和 policy 都允许升级时，才有第二次执行。

    Q15：Linux Sandbox 只使用 Landlock 吗？

    不是。当前主要路径是 bubblewrap 文件系统 namespace 加 seccomp；Landlock 是显式 legacy 路径之一。

    Q16：Apply Patch 失败会自动回滚吗？

    不会保证。它不是事务性的，部分 delta 可能保留。失败后应检查 git diff 和工作树。

    Q17：工具输出太大时 Codex 怎么办？

    进入模型 history 前按 byte/token budget 中间截断；原始 payload 可保留在 Rollout，整个 history 过大时再 compact。

    Q18：Rollout 有完整工具输出，模型就能重新读取吗？

    不一定。Rollout 服务恢复与审计，不会自动给模型一个 Rollout 读取工具。自定义工具应支持分页、搜索或结果 handle。

    Q19：输出截断和 Compaction 有什么区别？

    截断处理单个工具结果，不调用模型；compaction 处理整段历史，通常调用模型生成摘要或服务端 compaction item。

    Q20：Provider 报 context overflow 后会立即无限压缩重试吗？

    不会。普通 sampling 通常结束当前 turn并标记满窗，让下一 turn 预压缩。特殊 Guardian 路径可能同 turn 重试一次。

    Q21：Compaction 会保留哪些信息？

    Local compact 保留近期用户目标、summary 和当前 canonical context；并不保证无损。多次 compact 可能降低准确率。

    Q22：Compaction 请求本身也超窗怎么办？

    Local compact 从最老 history item 开始逐项删除，再重试 compact；只剩最小输入仍超窗则失败。

    Q23：为什么要有 Rollout 和 model history 两份视图？

    恢复需要比模型输入更多的状态；模型输入又必须受上下文预算、模态和配对规则约束。两者目标不同。

    Q24：Resume 如何选择历史起点？

    优先选择最新可安全重建的 compaction checkpoint，然后回放其后缀；没有可用 checkpoint 时重放全部可用 Rollout。

    Q25：Fork 与 Resume 有什么区别？

    Resume 延续同一个 thread；Fork 创建新 thread，并复制或引用父 history 前缀，可在指定用户边界截断。

    Q26：MCP 工具会受 Codex shell sandbox 保护吗？

    MCP 调用受 ToolRegistry 和 approval 管理，但远端服务的内部副作用不受本机 OS shell sandbox 自动限制。

    Q27：为什么 MCP 需要 immutable binding？

    保证模型看到的 schema、permission、timeout 与执行时 client/catalog revision 一致，避免热更新产生 TOCTOU。

    Q28：AGENTS.md 的作用域是什么？

    从项目根到当前目录逐层加载，override 文件优先；总量受预算限制，不可信项目不加载项目指令。

    Q29：Python SDK 与 TypeScript SDK 能力相同吗？

    不完全相同。Python SDK 直接使用 app-server；TypeScript SDK 基于 exec JSON 输出，能力面更窄。

    Q30：做企业集成应该直接调用 Core 吗？

    通常优先 app-server。它提供 thread/turn、通知、审批和动态工具协议，避免耦合 Core 内部 Rust 类型。

    Q31：Exec 模式能处理人工审批吗？

    它面向非交互自动化，默认 approval never，审批和用户问题通常被拒绝。需要交互时使用 TUI、IDE 或自建 app-server 客户端。

    Q32：模型工具名可以被外部插件覆盖吗？

    关键默认 namespace 名如 exec_command 有保留规则；重复外部工具通常先注册者生效并记录冲突。

    Q33：命令被分类为 Read 就一定安全吗？

    不一定。Read/Search/ListFiles 分类主要用于 UI/遥测；真正安全依赖 execpolicy、approval 和 OS sandbox。

    Q34：Environment variable secret filtering 是否可靠？

    只是风险降低。默认按 KEY/SECRET/TOKEN 等名称过滤，但可被关闭，也无法识别伪装变量或文件中的 secret。

    Q35：Multi-agent 子线程继承什么？

    可继承模型、provider、approval、sandbox、cwd、指令和 role overlay；准确行为由 child config 决定。

    Q36：Multi-agent 越多越好吗？

    不是。它增加 token、工具并发、历史传播和状态协调成本，应只并行真正独立的任务。

    Q37：哪些状态不应只放在内存中？

    影响 resume、fork 和下一次模型输入的状态应进入 Rollout、TurnContext、world state 或明确的持久化数据结构。

    Q38：如何调试“模型看到的内容不对”？

    按顺序检查 AGENTS/skills、Config layers、StepContext 工具目录、ContextManager history、truncation metadata、compaction replacement 和 app-server item 通知。

    Q39：如何调试“命令为什么被拒绝”？

    检查 ToolPolicy、execpolicy、approval policy、permission profile、sandbox platform、network proxy 与 hook。不要只看模型提示词。

    Q40：Codex Harness 最值得借鉴的设计是什么？

    统一 app-server 控制面、StepContext 一致快照、工具安全分层，以及 Rollout 与 model history 分离。

    31. 结论与落地建议

    核心结论

    1. Codex CLI 是完整本地 coding-agent runtime。 置信度：高。
    2. app-server 是多客户端统一控制面，Session/Turn loop 是运行核心。 置信度：高。
    3. 一个 turn 可包含多次 Responses sampling 和并行工具执行。 置信度：高。
    4. 安全来自 ToolPolicy、审批、execpolicy、OS sandbox 与网络控制的组合。 置信度：高。
    5. Rollout 保留恢复事实，ContextManager 生成受预算约束的模型视图。 置信度：高。
    6. 大结果先截断，长历史再 compact，真实 provider 超窗不进入无界重试。 置信度：高。

    团队行动建议

    1. 集成优先使用 app-server typed protocol；
    2. 固定 Codex commit/版本与配置 schema；
    3. 自定义工具强制声明权限、并行性、取消和输出预算；
    4. 大工具结果原生支持分页与句柄；
    5. 将 enterprise constraints 放入 managed requirements；
    6. 单独审计 MCP server、dynamic tools 和 hooks；
    7. 用真实平台测试 Linux/macOS/Windows sandbox；
    8. 做 compact -> resume -> fork 一致性回归；
    9. 多次 compaction 后主动启动新 thread；
    10. 不把 Rollout、telemetry 和 compliance audit 混为一谈。
