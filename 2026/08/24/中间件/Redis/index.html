    引言

    Redis是一个高性能、高可靠、高可扩展的 kv数据库。

    Redis高性能的原因：

    • Redis是内存数据库，大多数命令处理基于内存操作，读写快。
    • Redis是单进程线程处理网络请求，大多数命令是读和写io，不涉及计算，不需要多线程。这样避免了上下文的切换和锁。
    • Redis使用多路IO复用模型(select、poll、epoll)，可以高效处理并发连接。
    • Redis的底层数据结构很巧妙，包括简单冬动态字符串sds、跳表skip list、整数集合intset、压缩列表ziplist、快速链表quicklist、字典dict。

    设计键值数据库面临的问题

    三个问题

    现在，我们从零设计一个键值数据库，需要考虑以下三个问题。

    可以存哪些数据

    对于键值数据库而言，选型的重要因素就是它支持的value类型以及支持的操作。Redis本身支持String、哈希表、列表、集合、有序集合等应对不同业务场景。

    可以做哪些操作

    最基础的键值数据库操作包括：

    • PUT
    • GET
    • DELETE
    • SCAN（扫描一段范围）

    数据保存在哪里

    内存的特点是读写快，易丢失；磁盘的特点是持久化，读写慢。Redis为了保证性能，采用内存。

    键值数据库的基本架构

    键值数据库包括四部分：

    • 访问框架
    • 操作模块
    • 索引
    • 存储

    访问框架

    常见的访问框架有两种：

    • 以动态链接库.so 形式供外部使用 （RocksDB）
    • 通过网络框架以 Socket 通信形式提供操作接口 （Redis）

    通过网络框架访问的情况下，需要考虑单线程和多线程两种情况：

    • 如果一个线程既要处理网络连接、解析请求，又存储数据，一旦发生阻塞，线程就会阻塞。
    • 如果采用不同线程处理，则在访问共享资源时会产生线程竞争。

    索引模块

    索引模块的作用是快速根据key定位数据。索引通常使用哈希表、B+树、字典树等实现。Redis使用的哈希表，因为键值对保存在内存中，内存的高性能访问特性非常匹配哈希表O(1)的操作复杂度。

    对于列表、集合等复杂value结构，Redis也设计了专门的索引结构来支持复杂操作。

    操作模块

    索引模块定位到位置之后，就需要执行具体操作。

    • GET/SCAN：直接返回value值。
    • PUT：分配内存空间
    • DELETE：释放内存空间

    存储模块

    存储模块需要实现内存管理功能，并且为了每次重启后快速提供服务需要持久化功能。

    对于持久化功能的实现，如果每次操作都落盘，性能会非常差；如果周期性的落盘，会有丢失风险。

    Redis的更多扩展

    Redis在普通内存键值数据库的基础上，引入了更丰富的value类型、操作类型、高可用和高可扩展性。

    Redis 全景图

    • 高性能：线程模型、数据结构、AOF与RDB持久化、epoll网络框架
    • 高可靠：主从复制、哨兵、AOF与RDB持久化
    • 高可扩展：负载均衡、数据分片

    Redis的单线程高性能IO模型

    Redis的单线程指的是redis的网络IO和键值对读写由一个线程完成，但持久化、异步删除、集群数据同步都是额外线程实现的。

    为什么单线程

    当多线程操作同一个数据结构时会面临共享资源的并发访问控制问题：如果使用互斥锁，就会导致很多线程等待互斥锁，并行变串行，不仅没收益，还额外引入了上下文切换等问题；如果使用同步原语，会降低代码的可维护性。因此Redis采用了单线程。

    为什么单线程快

    一方面，Redis的大部分操作在内存完成，数据结构高效，因此单线程的执行效率本身高。

    另一方面，Redis采用了多路复用机制，在网络IO操作中能并发处理大量客户端请求。

    socket 通信中的 阻塞 io 模型

    处理一个Get请求，需要监听客户端请求（bind/listen），和客户端建立连接（accept），从socket中读取
    请求（recv），解析客户端发送请求（parse），根据请求类型读取键值数据（get），最后给客户端返回结果，即向socket中写回数据（send）。

    基于多路复用的高性能io模型

    阻塞模式下，如果accept或recv阻塞，会导致无法处理其他请求。因此，可以利用以下三个关键方法实现非阻塞模式：

    当Redis调用accept()但一直未有连接请求到达时，Redis线程可以设置监听套接字后返回处理其他操作，而不用一直等待。

    Redis 调用epoll机制，让内核来监听这些套接字，epoll提供了基于事件的回调机制。epoll的回调事件入队，redis使用单线程不断处理事件队列里的内容。

    Redis的数据结构

    键和值的结构组织方式

    为了实现键的快速访问，Redis使用了全局哈希表存储所有键值对。

    哈希表本质上是一个哈希桶组成的数组，每个桶保存了两个指针*key和*value，包括了所有的键值对。键映射到哈希值后，就可以快速定位哈希桶位置。

    但，哈希表一定要面临两个问题：哈希冲突，rehash。

    哈希冲突与渐进式rehash

    Redis使用链式地址法解决，可以参考 古法编程/哈希表.md。

    为了应对哈希冲突，Redis通常会额外准备一个备用哈希表，备用哈希表比当前哈希表大小大；当链式地址中的哈希冲突过长，则需要rehash，为备用哈希表申请空间，重新映射键值对。

    这个过程很耗时。Redis利用渐进式rehash：每次处理某个位置的请求的时候，才顺便完成对该位置rehash操作，这样将开销分摊到了多次请求。

    值的底层数据结构

    SDS

    简单动态字符串(Simple Dynamic Strings，SDS) 是Redis的基本数据结构，我们从以下几个设计目标来理解这个数据结构。

    设计目标一： “实现一个扩容方便且二进制安全的字符串”。

    [!NOTE]

    非二进制安全指的是在C语言中，如果字符串本身包含\0 字符，会被识别为字符串末尾，导致字符串被截断。二进制安全反之。

    通过设置单独的统计变量len 和 free 来保证二进制安全和得到字符串长度，内容通过柔性数组buf存放并暴露数组指针，让上层可以像C字符串一样读取和处理sds。

    struct sds {
  int len;
  int free;
  char buf[];
}

    所谓柔性数组，指的是他的地址和结构体是连续的，可以快速查找内存。

    设计目标二：不同长度的字符串其实没必要占用相同大小的头部，

    每个字符串的元信息都占用4字节太浪费了。因此，针对不同大小的字符串，衍生了多种sds。

    sdshdr5

    对于最短的字符串，使用1个flag字节来表示元信息，低3位存储类型，高5位存储长度。短字符串不需要free，因为修改后大概率也在32($2^5$ )字节内，无需扩容；即使扩容，也会直接修改类型，不会再使用sdshdr5 。

    struct sdshdr5 {
	unsigned char flags;
  char buf[];
}

    sdshdr8

    struct sdshdr8 {
  uint8_t len; // 当前长度
  uint8_t alloc; // 总长度，空闲长度free = alloc - len
  unsigned char flags; // 低3位类型，高5位预留
}

    SDS的扩容

    跳跃表

    对于有序数据，数组不便于元素插入和删除，链表查询效率低，平衡树或红黑树实现复杂，因此Redis采用了跳跃表。

    分层有序链表

    首先，为了解决链表查找效率问题，我们可以参考分层有序链表，从高到低进行查找。

    基于这种思想，跳跃表具有以下几个关键性质：

    • 分层。
    • 每层的链表是个有序链表，数据递增；
    • 除头节点外，层数最多的节点层高为跳跃表的高度。
    • 每个节点存储了本层到下个节点的跨度(span)。
    • 跳跃表有一个tail指针指向最后一个节点。

    跳表的时查找复杂度为 $O_(\log{N})$

    压缩列表

    压缩列表类似数组，在表头新增了 zlbytes列表长度， zltail列表尾偏移量，zllen列表entry个数 三个字段，并在列表尾巴新增了 zlend 标识列表结束。通过列表查找头和尾都可以 $O(1)$复杂度实现。

    不同数据结构的时间复杂度

    压缩列表（ziplist）之所以被称为“压缩”，是因为它通过特殊的内存编码方式，极大地减少了数据在内存中的占用空间。它的“压缩”主要体现在以下三个方面：

    变长编码（节省数值存储空间）

    在普通数组中，存储一个整数通常需要固定的 4 字节（int32）或 8 字节（int64），无论这个数有多小。

    而 ziplist 对整数采用了变长存储：

    • 极小整数：如果一个数字很小（比如 0-12），它甚至不需要额外的字节，直接嵌入到头部信息中。
    • 小整数：如果数字在 int8 范围内，只占 1 字节；int16 范围内占 2 字节；int24 占 3 字节。
    • 大整数：只有当数字真的很大时，才会使用 4 或 8 字节。

    压缩点： 避免了“大材小用”，存数字 1 只需要极少的空间，而不是固定的 4/8 字节。

    消除指针开销（节省结构空间）

    这是 ziplist 最核心的压缩手段。

    • 普通链表/列表：每个节点除了存数据，还需要存前驱指针和后继指针。在 64 位系统中，这两个指针就要占用 16 字节。如果你只存一个 “hello” (5字节)，实际内存消耗却是 5 + 16 = 21 字节，开销巨大。
    • ziplist：它是一块连续的内存块。它不需要指针来连接下一个节点，而是通过记录上一个节点的长度来推算下一个节点的起始位置。

    压缩点： 彻底去除了链表结构中昂贵的指针开销（每个节点节省 16 字节）。

    短字符串的特殊处理

    对于很短的字符串，ziplist 也会使用特殊的编码长度（例如用 1 个字节来表示长度，而不是像普通字符串对象那样有复杂的头部结构），进一步挤压每一比特的空间。

    特性 普通链表/数组 压缩列表 (ziplist) 压缩效果
    连接方式 指针 (Prev/Next) 连续内存，靠计算偏移量 省去了每个节点 16 字节的指针开销
    整数存储 固定 4 或 8 字节 动态 1, 2, 3, 4, 8 字节 小数字极度省空间
    内存布局 分散（可能碎片化） 连续紧凑 CPU 缓存命中率更高

    不过这种极致压缩也有代价，就是插入或删除元素时可能需要频繁地重新分配和拷贝整块内存。想不想了解一下Redis是

    Redis的持久化

    Redis的持久化有两大机制：AOF（Append Only File）日志 和 RDB 快照。

    AOF日志

    AOF是一种写后日志，即先写内存，再记日志。

    AOF日志写入机制

    对比数据库常用的写前日志模式，这样设计一个好处是可以免去对错误命令的语法检查，只有命令执行成功才会记录日志；另一个好处是不会阻塞当前请求的写操作。

    缺点是可能日志还没落到磁盘就宕机了导致数据丢失，而且由于写AOF日志也是主线程执行，会阻塞下一个请求。

    为了解决这两个缺点，AOF给我们提供了三种不同的写回磁盘策略配置项。

    • Always：每个写命令执行完都要立刻将日志写到磁盘。
    • Everysec：先在内存中维护，每隔一秒写一次磁盘。
    • No：由操作系统自行决定什么时候写回磁盘。

    AOF重写机制

    随着系统的使用，日志越来越多，文件开始膨胀，将面临文件大小超限、大文件操作效率低等问题，因此，需要引入AOF重写机制。

    重写机制会尝试用一条命令代替多条命令；对于有过期时间的数据，会使用带有时间戳的写入命令替代原来时间段的命令。

    AOF重写是由后台子进程 bgrewriteaof完成的，不会阻塞主线程。

    重写时，主线程fork出子进程 bgrewriteaof，此时主线程的内存也会在子线程中拷贝一份，新操作的日志会同时写到这两份内存的日志中。

    任务去重、消息重复消费问题

    通过 SETNX 判断是否已经执行，SET NX 是 SET 命令配合 NX（Not eXists）参数的一种用法。它的核心作用是：只有当指定的键（Key, 这里指的是唯一任务id）不存在时，才执行设置操作；如果键已经存在，则不执行任何操作*。

    异步 Agent 通过 MQ 返回结果时，使用Redis防止消息重复消费，保证幂等姓。

    熔断器

    • {agentId}:window
      • 作用：滑动窗口计数器。
      • 理解：用来记录最近一段时间内（比如最近10秒）该 Agent 的成功和失败调用次数。Redis 的 List 或 ZSet 结构非常适合做这种时间窗口统计。当失败次数超过阈值（比如50%的请求都失败了），就会触发状态变更。
    • {agentId}:openuntil
      • 作用：熔断截止时间戳。
      • 理解：这是一个“禁令”标记。一旦进入 OPEN 状态，系统会写入一个未来的时间戳。在这个时间点之前，所有请求直接拒绝，不再调用下游 Agent。
    • {agentId}:halfopen_probe
      • 作用：半开状态的探针锁。
      • 理解：这是为了解决“集群惊群效应”。当熔断时间结束进入 HALF_OPEN 状态时，如果集群有100个节点，不能让100个节点同时去试探下游是否恢复。利用 Redis 的原子性（如 SETNX），只允许抢到锁的那 1 个节点去发探测请求。

    熔断器生命周期

    • CLOSED (闭合/正常态)
      • 含义：一切正常，请求正常转发给 Agent。
      • 触发条件：在 window 窗口期内，统计到的失败率超过了设定的阈值。
      • 动作：系统判定 Agent 不可用，状态切换为 OPEN。
    • OPEN (开启/熔断态)
      • 含义：Agent 已“挂掉”，停止发送请求，直接返回错误或默认值（快速失败）。
      • 触发条件：预设的熔断冷却时间（openuntil=30）结束。
      • 动作：状态切换为 HALF_OPEN，准备尝试恢复。
    • HALF_OPEN (半开/探测态)
      • 含义：小心翼翼地尝试恢复。
      • 触发条件：放行的探测请求调用成功。
      • 动作：确认 Agent 已恢复，状态切回 CLOSED；如果探测失败，则重新回到 OPEN 状态并延长冷却时间。

    分布式锁

    为什么需要分布式锁

    假设 Octopus 部署三个节点：

    节点 A：原来执行任务 T1，后来宕机 
节点 B：SchedulerX 扫描到 T1 
节点 C：Callback 到达，也发现 T1 需要恢复

    此时 B 和 C 都可能尝试恢复同一个任务。

    没有锁时可能发生：

    B 恢复 T1 → 调用 Agent C 恢复 T1 → 再次调用 Agent

    后果包括：

    • 外部 Agent 被调用两次；
    • 最终消息重复推送；
    • Checkpoint 相互覆盖；
    • TaskCenter 重复上报；
    • 产生重复业务副作用。

    获取锁的方法

    SET lockKey ownerToken NX PX 60000
    • NX：Key 不存在时才写入；
    • PX：设置毫秒级过期时间；
    • ownerToken：当前持有者的唯一身份。

    callback bridge

    外部 Agent 的结果是异步返回的，而且可能回调到任意 Octopus 节点，如何把结果交给原来的执行流程，不能使用内存，因此需要借助Redis。

    Callback Bridge 的核心需求是低延迟、按 correlationId 动态唤醒；消息已经存入 Redis，Pub/Sub 只做可丢失的通知。若改用 MQ，仍需共享存储和节点路由，复杂度更高、收益有限。
