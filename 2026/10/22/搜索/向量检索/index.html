    向量检索技术全景：写给资深搜索工程师

    目标读者：深耕倒排检索多年的搜索工程师，对向量检索的认知停留在”会用 FAISS/Milvus”。本文打通两套世界观——从倒排的直觉出发理解 ANN，从搜索引擎的架构直觉理解向量系统的工程权衡。配套 60 分钟讲稿与 FAQ 另附。

    全文约 15000 字，建议配合讲稿按节分享。

    〇、为什么搜索工程师需要一个”翻译层”

    你熟悉的倒排检索解决的是集合匹配问题：query 分词 → 求交 docid 集合 → 打分排序。它的精度来自精确匹配，代价是语义鸿沟——”便宜的手机”搜不到”高性价比千元机”。

    向量检索解决的是几何邻近问题：query 和 doc 都映射到同一个向量空间，距离近 = 语义近。它天然跨越语义鸿沟，代价是放弃了精确匹配的确定性——你拿不到”满足条件的全部文档”，只能拿”距离最近的 K 个”。

    这个本质差异会向下衍生出所有技术分歧。后文会用一张对照表收束，但先记住三个不可调和的点：

    1. 倒排是过滤式（filter）语义，向量是排序式（rank）语义——两者融合时的语义冲突是工业界至今没有标准答案的问题
    2. 倒排的空间复杂度由词表决定，向量的空间复杂度由 N×d 决定——后者在十亿级数据上是硬伤，所以量化技术是向量检索的”生死线”，而非锦上添花
    3. 倒排的更新是增量的、确定性的；向量索引的更新是近似的、全局敏感的（新文档可能改变邻居拓扑）——这直接决定了向量系统的构建/更新架构

    一、数学层：距离、度量与归一化

    1.1 三种距离的等价关系

    • L2（欧氏距离）：‖x−y‖
    • 内积（IP）：x·y
    • 余弦（cosine）：x·y / (‖x‖‖y‖)

    关键事实：归一化后 L2 与内积等价。‖x−y‖² = ‖x‖² + ‖y‖² − 2x·y，当 ‖x‖=‖y‖=1 时最小化 L2 等价于最大化内积。这就是所有”攒批计算优化 normalize 逻辑”的数学依据——把归一化做进索引期，查询期只剩点积一种运算，SIMD 才能统一满载。

    对搜索工程师的提醒：如果你用的 embedding 模型输出未归一化向量（如某些 BERT 系列的 pooler 输出），内积 ≠ 余弦，选错度量会导致检索质量不可解释。实践上建议统一在入库前归一化，除非模型文档明确说内积训练目标（如部分对比学习模型用 unnormalized IP 训练）。

    1.2 精确 vs 近似：为什么必须近似

    暴力检索（flat/bruteforce）是 O(N×d) 每次查询。N=1 亿、d=768、AVX-512 单核约 200 GFLOPS 时，一次全量扫描约 1e8 × 768 × 2 / 2e11 ≈ 0.77 秒/核。听起来”还能忍”？但这是单查询的延迟，QPS 一上来自动雪崩。所以 ANN 的本质不是”图快”，而是用可控的召回损失换数量级的吞吐/延迟/成本——这个 trade-off 没有免费午餐，一切后面技术都在这条曲线上滑动。

    衡量 ANN 的标尺是 recall@k vs 延迟/内存 的 Pareto 前沿。工程上常引用 recall@10 ≥ 0.95 作为”上线可用”的经验阈值，但真正该看的是端到端指标（向量召回子链路对最终 NDCG 的贡献），这是搜索工程师比算法团队更有发言权的地方。

    二、索引层：三大流派

    2.1 IVF：从倒排直觉最容易理解的一派

    IVF（Inverted File）就是向量版的倒排：k-means 把空间切成 k 个 cell，每条向量归属最近质心，倒排链挂 cell→docid 列表。查询时只扫离 query 最近的 nprobe 个 cell。

    对照你熟悉的倒排：

    倒排概念 IVF 对应物
    term 质心（cell）
    posting list cell 内向量列表
    分词 归属最近质心（硬划分，1 条向量只挂 1 个链）
    查询 term 选择 nprobe 个最近 cell

    关键差异是硬划分带来的召回损失：每条向量只挂 1 个链，查询正好落在两个 cell 边界附近时，真最近邻可能在未探测的 cell 里。缓解手段是提高 nprobe 和多分配（一条向量挂多个 cell，换存储）；residual 编码（存”向量减质心”）降低的是 cell 内编码误差，解决的是另一个问题。

    IVF 的搜索工程师直觉：它和倒排一样有”词典倾斜”问题——数据不均匀时某些 cell 巨大，扫描退化。IVF-HNSW（用 HNSW 找质心）就是针对这个的修补。

    2.2 HNSW：当前工业界主流

    HNSW 是分层小世界图：上层稀疏长边负责”高速公路”快速逼近，下层稠密短边负责精确收敛。搜索从顶层入口贪心跳转，逐层下沉，底层用 ef 动态候选队列做 beam search。

    它的三个超参数直接对应倒排世界的概念：

    • M（每节点边数）：类似倒排的索引膨胀率，M 越大图越稠密、召回越高、内存越大。经验值 16–48
    • ef_construction：建图时候选队列深度，影响构建时间与图质量。经验值 100–500
    • ef_search：查询时候选队列深度，运行时可调——这是 HNSW 最被称道的特性：延迟和召回在查询时动态权衡，不用重建索引

    两个必知的工程事实：

    1. 构建是 O(N log N) 级但常数巨大：每条向量插入要做 ef_construction 次距离计算级别的图搜索。十亿级数据构建是天级任务，这就是”攒批计算优化构建速度 40%+”的产业背景——构建吞吐是 HNSW 落地大规模数据的瓶颈
    2. 内存是 4d+ 级/向量（float32 时）：1 亿 × 768 维 float32 原始向量 ≈ 300 GB，加上图边（底层每节点 2M 条）再叠约 5–15%（随 M 增大）。这是量化技术的直接动因

    删除/更新是 HNSW 的弱项：删除只能打墓碑（软删除），大量删除后图拓扑退化需 rebuild。搜索引擎的”文档全量+增量天级更新”节奏和 HNSW 天然冲突——工业界标准解法是分层多代索引（新生代小图 + 老生代大图，定期合并），这和你熟悉的全量/增量索引体系同构。

    2.3 压缩编码（PQ/RabitQ 系）：极限内存路线

    PQ（乘积量化）把 d 维切成 m 段，每段用 k-means 学一个 256 项码本，向量编码成 m 字节。距离用查表（ADC）：d(x,y) ≈ Σ 段距离表[x段码][y段码]，一次 L2 距离变成 m 次查表加法。

    • 压缩比：768 维 float32（3072 B）→ PQ m=32（32 B）≈ 96×
    • 代价：召回显著下降，通常 PQ 只做粗排/粗筛，配浮点重排
    • SQ（标量量化）是 PQ 的零训练退化版：每维独立线性切桶，int16 近无损（50% 压缩）、int8 轻损（75% 压缩）

    RabitQ（SIGMOD 2024）是这条线的当前 SOTA：随机正交旋转（保距）均衡各维能量后做 1 bit/维二值量化（32× 压缩）；距离估算采用非对称方案——库侧用二值码、查询侧保留浮点，配合预存的范数/残差标量做修正，推导出对真实距离的无偏低方差估计量，使极限压缩下召回仍可用。它支持 k-means 质心化的残差编码（训练成本集中在 KMeans）。在”内存极限 + 粗筛”场景（十亿级）正替代 PQ 的位置，VSAG、Qdrant 等系统已跟进集成。

    2.4 选型速查

    场景 推荐 理由
    < 100 万，召回要求高 Flat（暴力） SIMD 暴力扫延迟足够低，精确无损失
    千万级，通用场景 HNSW + SQ int16 召回/延迟/内存均衡最优
    十亿级，内存受限 IVF + RabitQ/PQ 粗筛 + 重排 内存是硬约束，压缩换规模
    增量频繁 分层多代 HNSW 解决软删除退化与构建吞吐
    延迟 P99 < 10ms 硬约束 HNSW（ef_search 可调） 查询期动态权衡是刚需

    三、计算层：SIMD 与攒批

    3.1 距离计算是整个系统的内层循环

    无论 IVF 扫 cell、HNSW 跳图、还是 ADC 查表，最终都落到”算距离”。这一层的优化对所有上层算法通吃，是投入产出比最高的工程优化点。

    SIMD 的收益结构（AVX2=8 float、AVX-512=16 float、NEON=4 float/次）：

    • 乘加规整：点积/L2 是完美 SIMD 场景，加 FMA（一次舍入）后单核吞吐 8–16 倍于标量
    • 整数更快：量化后同样位宽寄存器装更多元素（512 bit = 16 float = 32 int16 = 64 int8），SQ 与 SIMD 成对出现是乘法关系：SQ 省一半内存带宽，SIMD 让这带宽里算的距离数翻倍
    • 运行时分发：FAISS/hnswlib 都用 cpuid 检测按 AVX-512/AVX2/SSE/NEON 多套实现分发，云上部署要确认实际指令集（老机器 AVX-512 可能被禁用降频）

    3.2 攒批：构建期优化的三板斧

    HNSW 构建期距离计算占 95% 以上时间。攒批优化的三个层次：

    1. 批量矩阵乘：候选集 n 个向量凑成 n×d 矩阵，GEMV 一次算完。SIMD 满载、分支预测摊薄
    2. normalize 批处理：逐条”除以模长”改为预计算倒数表批量乘 1/‖x‖，除法→乘法，且和批量距离计算融合
    3. 内存布局：向量按 64B 对齐连续存储（AoS→SoA 视实现），prefetch 提前载入下一批候选

    综合 40%+ 构建提速的来源就是这三层叠加——不是单点魔法，是把”逐条函数调用”的 CPU 行为改成”流式批量”的 CPU 行为。

    四、系统层：从库到搜索引擎

    4.1 向量检索在搜索链路里的位置

    一个生产级语义检索系统的向量子链路：

    query → embedding 服务（GPU，批量化，P99 波动源）
      → 向量召回（ANN 索引，本节主角）
      → 重排（可选：交叉编码器 rerank，或浮点精确距离重排）
      → 与倒排/其他召回源 merge → 统一排序

    搜索工程师最该关注三个接缝：

    接缝 1：召回融合（RRF/加权 vs 过滤）。倒排召回和向量召回怎么合？工业实践三种模式：

    • 并联后融合：各自取 TopK，用 RRF（Reciprocal Rank Fusion）或加权融合。最常用，语义上”两个或”的宽松召回
    • 向量召回 + 倒排过滤（filter-aware search）：向量给邻居，倒排/属性做硬过滤。这是难点：过滤比例高时 HNSW 候选大面积被滤掉，召回崩塌。解法有 pre-filter（先过滤再搜，等价缩小搜索集，但图可能断链）和 in-filter search（图搜索时跳过被滤点，Milvus/阿里 Proxima 等有专门实现）
    • 级联：倒排粗筛 → 向量精排。类目清晰、类目数可枚举时（如商品搜索）很有效

    接缝 2：embedding 服务的延迟与成本。query 侧 embedding 是在线 GPU 服务，批量化后延迟从 20ms 到 200ms 波动。标准解法：双路（高频 query 缓存 embedding + 长尾实时算）、蒸馏小模型（如大模型 768 维蒸馏到 64 维 int8 量化模型）。embedding 成本常常超过索引成本，做架构预算时别漏算

    接缝 3：向量与倒排的存储融合。向量索引是”每条向量 4d 字节 + 图结构”的稠密数据，和倒排的稀疏 posting 差异巨大。工程上常见”分离存储 + docid join”，join 的成本和 docid 映射稳定性（倒排 docid 频繁复用/压缩，向量侧需要稳定内部 id）是隐藏工程量

    4.2 索引生命周期：与倒排全量/增量的同构

    搜索工程师的心智模型直接可迁移：

    倒排世界 向量世界
    全量索引 + 小时/天级增量 老生代 HNSW 大图 + 新生代小图（增量插入）
    增量段定期 merge 新生代满了 merge 进老生代（rebuild 或局部重建）
    实时性靠实时段（memory segment） 实时段用小图或暴力扫描，量小可接受
    删除靠 tombstone 同左，HNSW 软删除 + 定期 rebuild
    docid 稳定性靠外部映射 同左，向量内部 id ↔ 业务 docid 映射层

    差异点：向量 merge 不是倒排的归并排序，是部分 rebuild——图拓扑对插入顺序敏感，merge 时新图的邻居结构会整体变化。这是向量系统构建成本高的根因，也是”攒批优化构建速度”在产业叙事里分量重的原因。

    4.3 GPU 与异构计算

    • 离线构建：GPU 上暴力 kNN + 建图（如 RAFT/cuVS 路线）比 CPU 逐条插入快 1–2 个数量级，十亿级构建的主流选择
    • 在线查询：GPU 批量查询吞吐高但单查延迟不稳定，P99 敏感场景仍以 CPU 为主
    • 趋势：GPU 构建 + CPU 在线服务的异构组合是当前大规模系统的常见架构

    五、评测层：资深工程师的护城河

    向量检索的评测坑比倒排多，因为近似性让一切指标都有了噪声。

    离线评测链：recall@k（对暴力 TopK）→ recall@k（对业务标注真集）→ 端到端 NDCG/CVR。第一层是索引的事，后两层是系统的事，只看第一层上线会翻车（向量召回 recall 0.98 但端到端不涨的案例比比皆是——问题出在融合/重排/展示层）。

    必查的四个坑：

    1. 查询分布偏斜：离线评测用均匀采样的 query，线上是幂律分布。HNSW 的 ef_search 在头部 query（邻居密集）和长尾 query（邻居稀疏）上表现差异巨大，P99 由长尾决定
    2. embedding 版本升级：换模型 = 全量重建 + 空间语义全变。上线流程必须是新旧双索引灰度（影子流量比对召回差异），这和倒排”换打分公式可以灰度调参”完全不同
    3. 数据漂移：新数据持续入库后，cell/图的分布偏移，recall 缓慢下降无告警——需要定期抽样评测的看门狗机制
    4. filter 召回崩塌：带过滤条件的查询是最大隐藏坑，离线评测集必须覆盖高过滤比例场景

    六、收束：一张总对照表

    维度 倒排检索 向量检索
    语义 集合匹配（精确、可解释） 几何邻近（近似、不可解释）
    空间复杂度 由词表/链长决定 N×d 硬约束，量化是生死线
    更新 增量确定性 近似全局敏感，多代索引架构
    延迟调优 索引/缓存/链长 ef_search 查询期动态调
    评测 可确定性验证 带噪声，需多层评测
    融合 — filter-aware、RRF、级联三模式
    工程重心 分词/相关性/排序 量化/构建吞吐/融合接缝

    最后给一条经验判断：搜索系统的未来形态不是”向量替代倒排”，而是两者深度咬合的混合检索——倒排提供精确性、可控性和成本下界，向量提供语义泛化能力。你的倒排架构经验（全量/增量、docid 管理、灰度评测）几乎全部可迁移，需要新建的心智是”用近似性思维管理质量与成本的交换”。这条曲线怎么滑，正是量化、SIMD、RabitQ、攒批这些技术每天在推进的边界。

    向量检索技术 FAQ：高频问答

    配合《向量检索技术全景》与分享讲稿使用。按提问场景分组：选型、原理深挖、工程落地、评测质量。面向资深搜索工程师，答案按”结论先行 → 原理 → 工程含义”组织。

    一、选型决策类

    Q1：数据量一亿，QPS 500，P99 要求 20ms，选什么索引？

    结论：HNSW + SQ int16，ef_search 起步 64，按 P99 调。 原理：一亿 × 768 维 float32 原始向量约 300 GB，加图边约 5–15%（随 M 增大）。SQ int16 后约 165 GB，召回损失 <1%，内存带宽减半对 20ms P99 是实质收益。 工程含义：如果内存预算只有 100 GB 以下，退到”IVF + RabitQ 粗筛 + 浮点重排”；QPS 500 单机 HNSW 可扛（单查 ef=64 时约 0.1–0.5ms CPU），但 P99 由长尾 query 决定，压测时用线上分布加权（见 Q15）。

    Q2：百万级数据有必要上 ANN 索引吗？

    没有。100 万 × 768 维 SIMD 暴力扫描单核约 5–15ms，多核并行后 QPS 上千，且精确无召回损失。FAISS 的 Flat 索引即可。ANN 的价值从千万级开始显现，百万级上 HNSW 是给自己找运维负担。

    Q3：SQ、PQ、RabitQ 怎么选？

    按压缩需求分档：

    • 50%（int16）~75%（int8）：SQ。零训练、近无损、实现简单，默认选项。
    • 10–30 倍：PQ 或 RabitQ。PQ 需要 k-means 训练码本，召回损失明显，只做粗筛；RabitQ 同样要 k-means 质心（残差相对质心计算，构建时间大头在 KMeans），但同样压缩比下召回显著优于 PQ，2024 年后新系统优先考虑。
    • 32 倍以上极限：RabitQ 是当前 SOTA（VSAG、Qdrant 等已集成），配合浮点/SQ 重排组成两级流水线。 注意：压缩档位的选择依据是端到端召回对业务指标的影响，不是”越大越好”（见 Q4）。

    Q4：RabitQ 32 倍压缩这么好，为什么不全量上？

    因为压缩-召回的交换曲线在极端段最陡：从 float32 到 int16 近乎免费，从 int8 到 1bit 每进一步，召回掉得越来越狠。RabitQ 的修正项把”崩”变成了”可控损失”，但损失仍在。全量上 RabitQ 意味着所有查询的召回都压在这条曲线最陡的一段上，只有内存是硬约束（十亿级）时才值得。内存宽裕时，SQ int16 的近无损是更稳的默认。

    Q5：增量频繁的场景（媒体/Feed 流）怎么办？

    多代索引架构：老生代 HNSW 大图（天级全量构建）+ 新生代小图（小时级滚动）+ 实时段（内存暴力扫或小图）。新生代写满 merge 进老生代——注意向量的 merge 是部分 rebuild 不是归并（图拓扑对插入顺序敏感），merge 窗口的构建吞吐要用攒批优化兜底。这套和倒排的全量/增量/实时三段同构，可直接复用你们的调度体系。

    二、原理深挖类

    Q6：为什么归一化后 L2 和内积等价？

    ‖x−y‖² = ‖x‖² + ‖y‖² − 2x·y。归一化后 ‖x‖=‖y‖=1，前两项是常数，最小化 L2² 等价于最大化内积。工程意义：索引期统一归一化，查询期只需一种距离函数，SIMD 路径统一、normalize 可以批处理进构建流水线。 例外：少数对比学习模型用未归一化内积作为训练目标（MIPS 场景），此时强行归一化会破坏模型语义，换索引前先读模型文档。

    Q7：HNSW 为什么召回高？ef_search 调大的代价是什么？

    HNSW 的图结构保证了”任意两点间存在一条贪心可达的近邻路径”（navigable small world 性质），搜索是受控的 beam search：ef 越大，探索的候选越多，越不容易漏掉真实近邻。ef 调大的代价是线性的距离计算次数增长（大约和 ef 成正比），所以延迟和 CPU 成本线性上升。这就是”查询期动态权衡”：高峰降 ef 保吞吐、低峰升 ef 保召回。

    Q8：HNSW 删除为什么难？

    图节点删除会破坏邻居的连边，直接删可能让图断链（部分区域从入口贪心不可达）。工业实现都是软删除（墓碑标记，搜索时跳过但占内存），大量删除后图拓扑稀疏化，召回下降，需要定期 rebuild。这就是向量系统必须有多代/rebuild 机制的根因。

    Q9：PQ 查表（ADC）为什么快？

    查询向量到某 cell 的每段码本距离预先算好（每段一张 256 项的表），之后对库里每条向量算距离只需 m 次表查找 + 加法，完全不碰浮点乘法。m=32 时一次距离约 32 次内存访问加法，比浮点点积快一个量级，代价是每段只能用质心近似，误差叠加后召回明显掉。所以 ADC 定位是粗筛。

    Q10：RabitQ 的”误差修正”到底修正了什么？

    二值化后，用码直接算的距离是真实距离的系统性低估（量化丢掉的信息让向量都”挤到”了超立方体顶点附近）。RabitQ 用非对称估算——库侧二值码、查询侧保留浮点/低精度，预先存每条向量的范数和残差投影标量（每条向量几个浮点数），在估算公式里把它们乘回去，得到对真实距离的无偏低方差近似。效果是”码很粗，但估出来的距离排序基本对”——粗筛场景这就够用了，TopM 候选交给重排。

    Q11：SIMD 对所有距离函数都有效吗？

    规整的乘加循环（点积、L2、余弦归一化后）是完美场景。整数码的 popcount（RabitQ/PQ 二值路线）在 SIMD 下更快（一条指令 64 bit）。例外是非对称函数（如 jaccard、自定义加权），向量化收益递减。选型时确认你们用的库对目标度量有 SIMD 实现（FAISS/hnswlib 的内积和 L2 都有）。

    三、工程落地类

    Q12：向量召回和倒排召回怎么融合？

    三种模式按场景选：

    • RRF/加权并联：默认选择，实现最简单，语义宽松（”两个或”）。RRF 对分数尺度不敏感，比加权融合好调。
    • 向量召回 + 属性过滤：带结构化条件（类目、价格、状态）的查询。高过滤比例时召回会崩，需要 in-filter search（图搜索时跳过被滤点）或 pre-filter。这是三大接缝里最容易翻车的，见 Q16。
    • 级联：倒排粗筛 → 向量精排。类目可枚举、粗筛质量高的场景（商品搜索）效果好，向量只算头部候选，成本可控。

    Q13：query embedding 在线服务的延迟怎么压？

    三个手段叠加：高频 query 的 embedding 缓存（幂律分布下头部 query 覆盖大部分流量）；批量化（GPU 小批 5–10ms，大批吞吐高但延迟涨，按流量分档）；模型蒸馏（768 维大模型 → 64 维 int8 小模型，推理快一个量级，召回小幅下降）。注意成本大头常常在 embedding 不在索引，架构预算别只算存储。

    Q14：向量侧的 docid 怎么管理？

    向量索引需要稳定的内部 id（图节点、cell 成员），倒排的 docid 会复用和重压缩，两边不能直接共用。标准做法是向量侧维护独立 internal id → 业务 docid 映射（构建时固定、删除打墓碑），查询结果 join 回业务侧。隐藏成本在映射层的更新一致性和 join 的延迟，数据量大时这个 join 不是免费的。

    Q15：HNSW 上线后 P99 延迟毛刺，排查顺序？

    按翻车概率排：1）长尾 query——头部 query 邻居密集、长尾稀疏，P99 由长尾决定，检查 ef_search 是否需要按 query 频次自适应；2）过滤崩塌——高过滤比例查询不断扩大 ef 导致延迟飙升（看监控里”带 filter 的查询延迟分布”）；3）内存带宽竞争——SQ 后带宽需求减半，同机混布其他大内存服务时毛刺放大；4）NUMA 跨节点访问——大索引跨 NUMA 部署时延迟翻倍，绑定节点部署。

    Q16：带过滤条件的查询召回崩了，怎么办？

    先定位崩的模式：过滤比例多少（>80% 基本必崩）、过滤后集合是否还连通（图断链问题）。方案梯度：换 in-filter search 实现（Milvus/Proxima 有现成的）；过滤集大时 pre-filter + 局部图/暴力扫；过滤集小且可枚举时直接对过滤后集合暴力（倒排给出 docid 集合，向量侧只对这些算距离）。最后一条其实是”级联”的变体，类目清晰的场景往往是最优解。

    四、评测质量类

    Q17：离线 recall@k 达到 0.98，上线端到端没涨，为什么？

    recall@k 是索引对暴力 TopK 的还原度，只保证”向量找回了向量认为好的东西”。端到端不涨的可能：embedding 质量本身（向量认为好的和用户认为好的不一致）；融合层（向量召回被 RRF 权重稀释或重排压制）；展示层（召回对但排序被 LTR 压掉）。排查顺序：先做召回对业务标注真集的 recall（不是对暴力 TopK），再 ablate 融合和重排各层。

    Q18：换 embedding 模型怎么灰度？

    双索引并行 + 影子流量比对：新模型全量构建新索引，线上 query 同时打新旧两套（影子链路不返回），比对召回差异分布——不只是 recall，要看召回集合的差集在业务上是否可接受。灰度切流后保留旧索引至少一个完整周期做回滚位。切记：这和倒排换打分公式不是一个量级，排期按全量重建估。

    Q19：怎么发现数据漂移导致的召回缓慢下降？

    看门狗机制：固定一组锚定 query（覆盖头部+长尾+各过滤场景），每天对当日子库抽样跑评测，recall 曲线接监控告警。漂移的信号是 recall 缓慢下滑而索引未重建。多代索引架构下还要监控老生代/新生代的 recall 差异——新数据先进新生代，分布偏移先在新生代表现。

    Q20：评测集怎么构建才不踩”分布偏斜”的坑？

    两条原则：query 分布按线上幂律加权采样（不是均匀），保证长尾 query 有足够样本暴露 P99 问题；过滤条件按线上真实分布构造 case，特别是高过滤比例场景（Q16 的坑离线最容易漏）。标注真集用业务信号（点击/转化）+ 人工抽检结合，纯人工标注在语义检索场景成本高且和线上偏好有偏差。
