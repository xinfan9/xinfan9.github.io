    TF （词频）

    TF（Term Frequency，词频）就是某个词在文档里出现多少次，常见有两种写法：

    1. 原始词频（BM25 使用的是原始词频）
    $$ TF(t, D) = \text{词 } t \text{ 在文档 } D \text{ 中出现的次数} $$
    1. 归一化词频
    $$ TF(t, D) = \frac{\text{词 } t \text{ 的出现次数}}{\text{文档总词数}} $$

    IDF（逆文档频率）

    逆文档频率也叫稀有词权重，表示越少文档包含这个词，权重越高。

    $$ IDF(t) = \ln\left(1 + \frac{N - n(t) + 0.5}{n(t) + 0.5}\right) $$
    • $N$：文档总数。
    • $n(t)$：包含词 $t$ 的文档数。

    BM25

    $$ BM25(D, Q) = \sum_{t \in Q} IDF(t) \cdot \frac{f(t, D) \cdot (k_1 + 1)}{f(t, D) + k_1\left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)} $$
    • $f(t, D)$：词 $t$ 在当前文档出现的次数。
    • $ D $：当前文档的词数。
    • $\text{avgdl}$：所有文档的平均词数。
    • $k_1$：控制词频收益的饱和速度，常用 1.2～2.0。
    • $b$：控制长度校正，常用 0.75；0 表示不校正。

    两个关键点：
    词频会饱和：出现 20 次的贡献，不是出现 2 次的 10 倍。
    长文档会被校正：长文档天然容易包含更多查询词，不能因此占便宜。

    倒排索引

    一、倒排索引的核心数据结构

    倒排索引本质是 term → 文档列表 的映射，Lucene 里分三层：

    • Term Index（词项索引，.tip 文件）：FST（Finite State Transducer）结构，把 term 前缀共享压缩在内存里，作用类似 B+树的非叶子层——先在内存定位 term 大致在 .tim 的哪个 block，避免全量 term dict 进内存。
    • Term Dictionary（词典，.tim 文件）：排序后的 term 列表（按 UTF-8 字节序），分 block 存储，block 内做前缀公共压缩 + 差值编码。
    • Posting List（倒排链）：每个 term 对应一组文档，每个 posting 包含：
      • docID（delta 编码 + PackedInt/BLOCK 压缩，默认每 128 个 docID 一个 block）
      • term freq（出现次数，用于打分）
      • position / offset（可选，用于短语查询、高亮，存 .pos）
      • 跳表（Skip List）：posting list 太长，做 block 级跳跃指针，支持 O(log n) 的交集跳转和 WAND 剪枝

    配套还有正排结构：Stored Fields（.fdx/.fdt，原文存储，行存）和 DocValues（列存，用于排序、聚合、脚本取值，避免回表）。

    二、索引写入流程

    一次文档写入的完整链路：

    1. Analysis 分词：文档经过 Analyzer（分词器 + 小写化 + 停用词等 filter），产出 term 序列。ES 默认 standard 分词，中文常见 ik。
    2. IndexWriter 写入内存 buffer：Lucene 的 indexing buffer，同时按 field 结构写入（倒排、DocValues、Stored 各自的内存结构）。写入同时记 translog（ES 层的事务日志，保证 crash 不丢数据——注意这是 ES 的机制，Lucene 本身没有）。
    3. Refresh → 生成 segment：buffer 刷成一个新的 segment（段），写入文件系统缓存并打开索引句柄，此时文档可被搜索——这就是 ES 的“近实时”（默认 1s，NRT）。段是不可变的（immutable），删除不真删，只在 .liv（liveDocs 位图）里打删除标记，等 merge 时物理消除。
    4. Flush / commit：segment fsync 到磁盘，清空 translog。
    5. Merge（段合并）：小段太多会拖垮检索（每次查询要打开所有段），由 TieredMergePolicy 按段大小分层合并；删除的文档在合并时被真正丢弃。merge 在后台线程做，是 IO/CPU 大户，ES 的 force merge 就是手动触发合并。

    不可变性是 Lucene 设计的基石：不需要锁就能并发读、内核 page cache 天然充当索引缓存、压缩率可以做得很激进（数据不变可以全量预计算编码）——代价就是更新=标记删除+重写，靠 merge 收敛。

    三、检索执行流程

    1. 查询解析：query DSL → Query 对象（TermQuery/BoolQuery/PhraseQuery…）。
    2. 词典查找：经 FST 定位到 term，拿到 posting list 的文件偏移，读出倒排链。
    3. 倒排合并：多个 term / 多个子句的文档集合做交并：
      • 跳表 + 按 docID 长度排序（最短链驱动）加速交集
      • 粗排 TopK 用 WAND / Block-Max WAND（Lucene 的 BS1/BS2 scorer）跳过不可能进 Top K 的文档，避免全量打分
    4. 打分：默认 BM25（ES 5.x 后取代 TF-IDF）。核心改进：词频饱和（k1 参数，TF 线性增长改为对数饱和）、字段长度归一化（b 参数，短字段加权，惩罚长字段）、IDF 项。BM25 现在是 Lucene 的默认 Similarity。
    5. 短语/位置查询：读 .pos 里的 position 列表，做位置对齐匹配（slop 控制）。
    6. 取回字段：TopK 文档回 Stored Fields 取 _source，或走 DocValues 做排序聚合。

    高频问题

    ES 侧机制类：

    • refresh / flush / translog / merge 四者的区别和作用——最高频，几乎必考。重点讲清“可搜索≠落盘”，refresh 决定可见性，translog 决定持久性。
    • 写入后为什么搜不到 / near-real-time 原理：refresh_interval 机制。
    • segment 不可变的优劣：缓存友好、无锁并发、压缩激进 vs 更新代价、小段开销、依赖 merge。
    • 深分页问题：from+size 每个分片要取 from+size 条在协调节点归并排序（二次排序，堆内存爆炸）；ES 用 max_result_window 默认 10000 兜底；替代方案 search_after（基于上一页排序值的游标，只能顺序翻）和 scroll（快照式批量导出，非实时）。
    • query context vs filter context：query 要算分走 BM25；filter 不算分，结果可缓存（位图/bkd 缓存），bool 里的 filter/must_not 属于后者——考点是“哪些查询条件应该放 filter”。

    Lucene 数据结构类（区分资深的分水岭）：

    • FST 原理：前缀+后缀共享的有限状态机，内存占用极小（可比 term 总量小一个量级），O(len(term)) 查找。追问通常是“为什么不用 B+树/哈希”——哈希不支持前缀/范围查询且内存大；B+树节点冗余大。
    • posting list 压缩：delta 编码 + FOR（Frame of Reference，按 block 用最小位数存储）+ 跳表。
    • DocValues 为什么存在：倒排做不了排序/聚合（回表太慢），列存一次性顺序读。顺带会问 BKD-Tree（数值/地理范围查询的 multidimensional 结构，替代早期的 precision tree）。
    • 删除文档的可见性：.liv 位图，merge 才物理删除；所以大量删除重建场景（如你做全量索引切换）会主动 force merge。

    打分类：

    • BM25 vs TF-IDF：词频饱和、长度归一、IDF 平滑，三个公式差异要能写出来。
    • 相关性与性能矛盾：WAND 剪枝原理（跳过 even 打最优分也进不了 TopK 的文档）。

    分布式类（ES 特有）：

    • 分片路由：shard = hash(routing) % num_primary_shards，所以主分片数建好后不能改。
    • 写入一致性：primary→replica 流程、wait_for_active_shards、translog 在 replica 上也写。
    • 段合并与 replica 一致性：各分片独立 merge，段结构不必一致，但文档集合语义一致。

    一、B+树 vs FST 具体区别

    先给结论：它们不是同一竞争维度的选择——B+树为“可变有序数据”设计，FST 为“静态只读词典”设计。Lucene 选 FST 的前提是段不可变，词典一次构建、永不修改，才敢用构建时代价换取极致的查询性能和内存占用。

    维度 B+树 FST
    本质 多路平衡搜索树：内部节点做路由，叶子存 key+数据指针，叶子间链表相连 最小化有限状态转换器：term 的公共前缀共享路径，公共后缀共享终止子图
    可变性 支持原地增删改（节点分裂/合并、页内挪动） 构建后不可变，更新只能重建
    空间 每 key 在多层节点冗余出现，节点间靠指针连接，空间 ≈ 数据量×系数 前后缀全共享 + 转移边带输出值，空间可小于原始 term 集合本身
    查找复杂度 O(log N)，树高通常 3~4（磁盘友好，节点对齐页） O(len(term))，与 term 总量无关，只与查的词长度有关
    前缀/模糊/范围 范围查询强（叶子链表顺序扫），但前缀要定位下界后扫一段 天然前缀树语义：前缀=状态节点，范围=有序遍历状态机，模糊/补全直接扩展（Lucene suggest 模块就是 FST）
    数据布局 节点=磁盘页，随机 IO 每层一次 编码成紧凑字节数组，整体常驻内存，无指针
    定位结果 叶子节点存数据指针/行 ID FST 是 transducer：每条边带输出值，走完一条 term 路径累计的输出直接算出该 term 在 .tim 里的 block 偏移——不需要存任何显式指针

    FST 比 trie 强在哪（追问点）：trie 只共享前缀，后缀不共享；FST 构建时把所有 term 排序后做最小化（minimize），等价的后缀子图合并成一个。比如 cat / can / dog —— trie 里 at 和 an 是两条独立路径，FST 会把它们压缩共享。再加上 transducer 的边输出值复用（前缀 term 的输出可以由后缀 term 的输出差值表示），所以一个亿级 term 的词典，FST 可能只有几十 MB，放进内存毫无压力。

    为什么哈希也不行（完整追问链）：哈希 O(1) 精确查询比 FST 快，但①不支持前缀/范围/通配/模糊，而搜索词典必须做 ab*、ab..f 这类查询；②哈希要存完整 term 字符串本体，内存是 FST 的一个量级以上；③哈希无序，merge 时无法做顺序归并。

    面试一句话总结：“B+树是磁盘时代的动态索引，用树高换页级 IO；FST 是内存时代的静态词典，用不可变性换共享压缩和 O(L) 查找。Lucene 词典是只读的，天然适合 FST——这正是段不可变这个架构决策在数据结构层的投影。”

    二、按索引中某字段排序的实现

    分三层回答，层层递进，这是面试官爱挖的链路：

    1. 检索时排序：DocValues 列存（核心机制）

    “排序依据的字段不走倒排，走 DocValues 列存——按 docID 顺序密排的字段值数组。流程是：倒排检索 + BM25/WAND 拿到候选 docID 流 → collector 维护一个 size=K 的优先队列（小顶堆）→ 每来一个 doc，用 docID 做偏移去 DocValues 里 O(1) 取该字段值 → 和堆顶比较决定是否换入。最终堆里就是 TopK。”

    关键细节（加分项）：

    • text 字段不能直接排序：text 被分词成多个 term，一个 doc 有多个值无法比较。必须用它的 keyword 子字段（field.keyword），单值可排序。这是最常见的实操坑。
    • DocValues 三种物理编码，面试可提：SORTED（值去重按字典序编号，每 doc 存 ord——枚举型字段压缩率极高）、SORTED_NUMERIC（数值差值编码）、DENSE/GENERIC。为什么编码重要：排序字段相邻 doc 值往往相似，差值+block 压缩后顺序扫很快。
    • 排序字段要禁打分剪枝的联动：sort by field 时相关性分数不再决定 TopK，BM25 的 max_score 优化、track_total_hits 计数都会相应调整，_score 可能为 null。
    • 老机制 fielddata（query 时从倒排反向构建 doc→value 映射，放 JVM 堆）：慢且吃堆内存，现已被 DocValues 取代——被问到 fielddata 就是送分题，答“DocValues 建段时预构建列存，fielddata 是查询时懒构建的堆内缓存”。

    2. 索引物理排序：index sorting（进阶考点）

    “ES 6.0+/Lucene 6.5+ 支持 index.sort，在建索引时就把段内文档按指定字段物理排序——即 docID 的编号顺序 = 字段排序顺序。这不是查询时排序，而是让数据落盘时就‘排好’。”

    三个收益：

    1. 查询提前终止：sort by 该字段时，段内文档已按此序排列，扫到前 K 个就能确认后面不可能更优，直接 truncate 提前结束整个段——查询从 O(命中数) 降到 O(K)，这是最大的性能收益；
    2. 压缩率提升：DocValues 和 Stored Fields 中相邻 doc 值相似，差值编码效率大幅提高；
    3. 范围类 filter 配合 docID 有序可整段跳过。

    代价：flush 时要在内存 buffer 内对文档先排序再编码，写吞吐下降——所以它适合读多写少、且查询固定按某字段排序的场景（比如日志类索引按 timestamp 排序是教科书用法）。

    3. 分布式归并（ES 层收尾）

    “单分片内拿到 TopK 后，每个分片返回自己的 Top (from+size) 条（带着排序值和 _shard_doc tie-break），协调节点做归并排序取全局 TopK。这里有稳定性的坑：如果排序字段值相同，不同分片返回顺序不稳定会导致翻页重复/丢失，ES 内部用 _shard_doc 隐藏字段做确定性 tie-break——深分页讲 search_after 时把这点带上。”

    面试综合陈述模板

    “字段排序分三个层面：微观上排序值存在 DocValues 列存里，检索时 collector 维护 TopK 堆，用 docID 直接偏移取列存值比较，text 字段要靠 keyword 子字段；中观上可以用 index.sort 让段内 docID 物理有序，换来提前终止和更高压缩率，代价是写入时排序；宏观上各分片本地 TopK 后由协调节点归并，同分片内 tie-break 保证稳定。整条链路体现的设计思想是：排序和检索解耦——倒排负责‘找谁’，列存负责‘怎么排’，物理预排负责‘排得快’。”

    两个问题都建议并入你的追问链：B+树 vs FST 挂在“词典结构为什么这样设计”的追问分支下，字段排序挂在“DocValues 存在的意义”分支下（第一问必然引出第二问）。需要我把这两节合入之前的面试文档吗？

    如果有多个排序字段呢

    2026-10-26 15:27:39

    多字段排序是个很好的追问收口点，继续按机制层展开。

    结论先行

    多字段排序 = 字典序（lexicographic）比较的复合比较器：按 sort 数组顺序逐字段比较，第一个字段分不出胜负才看第二个。实现上不是“排多次”，而是一个复合比较器一次遍历搞定。

    一、ES 查询层的语义规则

    GET /idx/_search
{ "sort": [
    { "category": "desc" },
    { "price": "asc" },
    "_score"
]}

    规则要点：

    • 字典序语义：先按 category 降序；category 相同才比 price 升序；再相同才比 _score。sort 数组里前面的字段优先级高，与 SQL 的 ORDER BY a, b 一致；
    • _score 可以混排在任意位置，实现“相关性为主、字段值做 tie-break”或“字段为主、相关性微调”两种模式；
    • missing 值处理是实操坑：缺字段的 doc 用 missing: "_last"（默认）或 _first 决定它排哪头——因为底层比较器遇到缺失值必须返回一个确定的三值结果，这是多字段比较器必须显式定义的分支；
    • text 字段同样不能直接排序，走 field.keyword 子字段。

    二、Lucene 底层：复合比较器

    单字段排序时，collector 的 TopK 堆用该字段的单值比较器；多字段时 Lucene 把多个 FieldComparator 串成复合比较器：

    • 每个 doc 到来时，按序取每个字段的 DocValues 值（docID 做偏移，每字段一次 O(1) 取值，多字段就是 K 次顺序读，DocValues 列存本来就为这种顺序扫描优化）；
    • 从第一个字段开始比较，遇分歧立即返回，后续字段不再取值——所以“前置字段区分度高”时，实际取值次数远少于字段数；
    • 堆中每个条目存的是复合排序 key（各字段值组成的元组），进堆出堆都用这个 key 比较。

    性能特征（追问点）：排序字段越多，每个候选 doc 的取值和比较成本越高，但仍是 O(命中 × 字段数)，且得益于提前分歧，实际开销取决于前置字段的区分度——面试可以点出“把高区分度字段放前面”既是语义优先级问题，也是性能优化。

    三、index.sort 的多字段物理预排（进阶）

    index.sort 同样支持多字段：

    { "index.sort.field": ["category", "price"],
  "index.sort.order": ["desc", "asc"] }

    关键机制：段内 docID 编号 = 多字段字典序排列结果，所以 docID 本身就是复合排序键的物化。

    有一个精巧细节（加分项）：升序和降序混排怎么物理实现？ Lucene 用“值变换”技巧——降序字段在编码进 DocValues 保留的排序视图时对值做反转（数值取反/翻转符号位，字符串用降序的 ord），这样物理上始终按字节升序遍历就等于逻辑上的混合方向。也就是说底层统一成一种单调序，方向在编码层解决。

    多字段 index.sort 下的收益变化（要诚实）：

    • 提前终止（early termination）依然成立，但只在查询的排序规则与 index.sort 的字段前缀完全一致时才能 truncate；如果查询按 (category, price) 排而物理序是 (category, price, timestamp)，前缀匹配仍可提前终止；如果查询按 price 排（跳过了前置字段），物理序无效，退回全扫+堆；
    • 字段越多，写入时排序成本越高（flush 前要对全 buffer 文档做字典序排序），且前缀约束越强，查询必须“迁就”物理序——所以多字段 index.sort 实际上适合查询排序模式高度固定的业务。

    四、分布式归并与稳定性

    多字段让 tie（排序值完全相同）概率下降，但没有消除：各分片本地 TopK → 协调节点按同一复合比较器归并。跨分片 tie-break 依然靠 _shard_doc 保证确定性翻页。深分页 search_after 的游标值此时是多字段值元组——search_after 传的是上一页最后一条的各排序字段值数组（加 _shard_doc），这也是为什么 sort 字段里放一个唯一字段（如 _id 或时间戳）是最佳实践：让复合键全局唯一，彻底消除 tie。

    五、HA3 对照

    正排 profile 多列 + 排序表达式：HA3 的 RankProfile 里 sort by 多个 attribute 本质也是复合比较，seeker 层预排/裁剪与物理序的联动思想同 index.sort——可以说“多字段字典序 + 列存取值 + 唯一键收尾 tie-break”是搜索系统通用三件套。

    一句话总结（挂到追问链）

    “多字段排序是复合比较器的字典序：排序数组顺序即优先级，取值按序、遇分歧即止，所以高区分度字段前置既是语义也是性能优化；index.sort 多字段让 docID 物理化复合序，方向混排靠值变换统一成单调序，但提前终止要求查询排序与物理序前缀匹配；收尾靠唯一字段（时间戳/_id）消除 tie，search_after 游标就是复合键元组。”

    详细介绍FST

    2026-10-26 15:28:15

    FST 值得单独深挖——它是 Lucene 面试里“数据结构分水岭”题的满分答案。我按演进 → 结构 → 构建 → Lucene 落地 → 能力边界五层讲透。

    一、定位：FST 是什么

    一句话：FST（Finite State Transducer，最小化有限状态转换机）是一个“有序字符串 → 值”的映射函数。普通自动机（DFA）回答“这个字符串在不在集合里”，FST 还能回答“它在集合里的话，对应的输出值是什么”。

    Lucene 用它做 term → .tim 文件 block 偏移的映射——即用 FST 把整个词典编码成一块极小的、可全量放进内存的查找结构。

    理解 FST 要走两步演进：trie → DAWG → FST。

    二、从 Trie 到 DAWG：后缀共享

    Trie 只共享前缀。存 bat / cat / catnap：

    Trie（前缀共享）:
        root
       /    \
      b      c
      |      |
      a      a
      |      |
      t      t------n
             |      |
            (F)     a
                     |
                     p
                     |
                    (F)

    bat 和 cat 的公共后缀 “at” 在 trie 里是两份独立拷贝。词典越大，这种冗余越夸张。

    DAWG（有向无环词图）= trie + 最小化：构建完成后把“结构完全相同”的子图合并。上图中 cat 路径上的 a→t 子图和 bat 路径上的 a→t 子图完全等价（都只通向终态），合并：

    DAWG（前缀+后缀共享）:
        root
       /    \
      b      c
       \    /
        \  /
         a
         |
         t------n
         |      |
        (F)     a
                 |
                 p
                 |
                (F)

    “at” 只存一份。这就是最小化（minimization）：等价状态归一。对真实词典（亿级 term，大量后缀重叠，比如所有以 -ing/-tion 结尾的词），DAWG 可以把内存压到原始字符串的几分之一。

    三、FST：给 DAWG 装上“输出”

    Transducer 与 DFA 的唯一区别：边（arc）上带输出值（output），终态可以带 final output。查一个 term，沿路径把所有边的输出累加，再加上终态的 final output，就是这个 term 的映射值。

    例：把三个 term 映射到 .tim 中的 block 偏移（有序，输出单调递增）：

    • cat → 100
    • catnap → 112
    • dog → 200

    编码成 FST：

    FST:
        root
       /  \
   c[100]  d[200]
      |      |
      a      o
      |      |
      t      g → (F)
      |           位置 200 的查询路径: 200
     (F,100)
      |
  ————n[12]————  ← catnap 在分歧点分出的新弧
      |
      a
      |
      p
      |
     (F)

    查询走读（这是面试必演示的）：

    • 查 cat：root –c(100)→ –a→ –t→ 到终态，路径输出和 = 100，终态 final output = 0，结果 100 ✓
    • 查 catnap：走到 t 之后继续 –n(12)→ a→ p→ 终态，100 + 12 = 112 ✓
    • 查 dog：d(200)→o→g→终态，200 ✓

    精妙之处（输出共享）：cat 和 catnap 共享整条 cat 路径，路径上的输出 100 只存一份；两者的差异 112−100=12 恰好放在分歧弧 n 上。这是 FST 的构建算法自动计算的——每个输出只在“必须区分的弧”上存一次，共享路径上零冗余。Lucene 利用了 term 输出（文件偏移）单调递增的性质进一步把输出编码成差值，进一步压缩。

    所以 FST 的空间可以小于所有 term 字符串本身：字符靠前后缀共享，输出靠分歧点共享，双维度去冗余。社区经典实测（Robert McCandlic，Lucene committer）：OpenStreetMap 900 万条街道名，FST 编码后约 10MB——比原文小一个量级，且查询速度与 HashMap 相当。

    四、构建算法：有序插入 + 冻结 + 最小化

    FST 要求输入按字典序排序（Lucene 词典本来就排序，天然满足）。核心是 Daciuk 增量最小化算法：

    1. 逐个插入 term。插入新 term 时，先沿现有 FST 走出与前一个 term 的最长公共前缀；
    2. 公共前缀之后的旧节点冻结（freeze）：因为输入有序，后续任何 term 都不可能再从这些节点分叉出去（未来 term 与它们的关系最多是公共前缀）——所以它们定型，可进入最小化；
    3. 冻结的子图在注册表（registry，按结构哈希）里查找等价状态，找到就合并指针（“at” 合并就发生在这里）；新 term 的剩余字符追加新弧；
    4. 重复直到输入结束，最后全树冻结。

    复杂度：构建 O(总输入字节数)（均摊），查找 O(len(term)) 与词典规模无关——这是与 B+树 O(log N) 的本质差异，面试点出来很加分。

    为什么必须排序：无序输入无法判定“这个节点不会再被扩展”，只能全量构建后离线最小化，内存峰值和构建时间都不可控。这也解释了 FST 只适合一次性构建、只读的场景——和 Lucene 段不可变完美咬合。

    五、Lucene 中的落地

    • 存哪：序列化进 .tip 文件，整体常驻内存（page cache + JVM 堆外/堆内按版本实现）。每个 field 一棵 FST。
    • 输出是什么：term 所在 .tim block 的文件偏移。定位 block 后，block 内 25~48 个 term 做前缀压缩 + 线性/二分扫描，找到精确 term 及其 posting list 指针。
    • 编码细节：每条弧 = label 字节 + 输出值（vlong 变长编码）+ 目标节点地址；节点内弧按 label 有序排列支持二分；root 弧单独缓存（几乎所有查询第一步走 root）。Lucene 还做“每弧最小字节数”打包（先统计 block 内弧的最大编码长度再统一定长）。
    • 不只是词典：Suggest 模块（自动补全/拼写纠错 AnalyzingSuggester）、正则/通配/模糊查询的 Levenshtein 自动机、多 term 交集（intersect 操作）都构建在自动机体系上——FST 是 Lucene 的基础设施而非单一 trick。

    六、能力面与局限（收口）

    能做：精确查找 O(L)；前缀查询（走到前缀末状态，其可达子图就是所有候选——autocomplete 天然实现）；范围查询（在状态机上按序枚举）；模糊/正则（把 pattern 编译成自动机与词典 FST 求交）；merge 时多路归并（自动机有序遍历）。

    局限：不可变（更新=重建，依赖上层段机制规避）；构建需要输入有序且吃内存（构建期临时节点 + registry）；只适合“字符串键→小整数值”类负载（值域大则输出编码膨胀）。

    面试陈述模板：“FST 是‘字符串→值’的静态映射函数，trie 提供前缀共享，最小化提供后缀共享，transducer 的弧输出提供值共享——三重去冗余让它比原始 term 集合还小，常驻内存做词典定位。构建依赖输入有序，用冻结+registry 增量最小化，O(n) 构建 O(L) 查询。它与段不可变互为因果：因为段不可变，词典可以一次构建只读；因为 FST 只读，Lucene 才敢把 refresh 做得这么轻。选它而不是 B+树，是因为 B+树的可变性在只读词典上是纯开销，而它换不来 FST 的前缀语义和量级压缩。”

    追问链（挂文档里）：

    • 为什么不用哈希 → 无前缀/范围/归并语义，且要存 term 本体
    • 为什么不用 B+树 → 磁盘导向设计，节点冗余大，O(log N) 依赖规模
    • 查找复杂度多少、和词典大小有关吗 → O(L) 与 N 无关，关键差异
    • 怎么构建、为什么要求有序 → 冻结正确性依赖有序
    • 内存为什么小 → 前缀/后缀/输出三重共享，附实测数字
    • FST 在 Lucene 还用在哪 → suggest、模糊/正则自动机、intersect
    • 更新怎么办 → 不可变，段级重建 + merge 归并
