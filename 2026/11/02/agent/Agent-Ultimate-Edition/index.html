    SSE 基本概念

    SSE 是什么：HTTP 长连接上的服务端单向推送协议，Content-Type: text/event-stream。传输格式是极简文本协议——每个事件由若干 字段: 值 行组成，空行分隔事件：

    event: processing data: {“content”:”你”} event: complete data: {“content”:””}

    浏览器侧用 EventSource（或 fetch 流式读取）消费；服务端主动写、客户端被动收，只能一条 HTTP 连接从头用到尾——这正是它和 WebSocket 的本质区别（WS 是双向全双工），也是”LLM 流式输出”天然适配 SSE 的原因：token 是单向流，不需要双向通道，却需要 HTTP 原生能力（网关、鉴权、CDN）。

    核心特点：

    • 单向：只能服务端→客户端；
    • 纯 HTTP：过代理、网关、鉴权零成本，天然兼容（LLM token 流式输出的标准选择）；
    • 内置断线续传：消息带 id:，客户端重连带 Last-Event-ID 补收增量；
    • 自动重连：浏览器 EventSource 断了自动重连，还能用 retry: 建议间隔；
    • 弱点：连接即会话——断连意味着状态丢失；每会话常驻一条挂起连接，空闲也有成本；对无状态水平扩容不友好（长连接粘在单实例上）。

    三个协议级限制要心里有数：旧浏览器没有原生 EventSource（fetch 流式读取兜底）；HTTP/1.1 同域 6 连接上限（HTTP/2 多路复用解决）；id: + Last-Event-ID 是断线重连的原生钩子。

    一条 chunk 的完整旅程

    Agent 平台里，模型回复从生成到用户看到，是一条两段背对背的 SSE 管道：模型→平台是第一段，平台→客户端是第二段，中间隔着线程桥接、内部事件分发、节流三层转换。

    模型 → 平台：SSE 调用器

    阻塞读 + Sinks 桥接：用同步 HTTP 客户端建流式连接、逐行读取模型返回的 SSE 响应，整个读取过程放到弹性线程池执行，不占用 event-loop；每读到一个有效 chunk 就向 Sinks 发射。方法返回 Sinks 对应的响应式流——调用方拿到流时实际读取在后台异步进行。

    三类特殊行：[DONE] 标记结束读取；usage-only chunk（请求时开启用量上报，上游在流末尾多回一个只含 usage 的块）只供访问监控日志、不转发给业务层——计费 chunk 和业务 chunk 分流，流式归账的干净做法；空 delta 块（finish 的空壳）直接过滤。

    首帧埋点：首 token 延迟只记一次；连接层监听器区分”新建连接 vs 复用连接”的建连耗时——首 token 延迟拆到连接层定位。访问日志每条流记一次（含用量和首 token 延迟），不是每 chunk 一次。

    错误进流不抛出：HTTP 失败或读取异常 → 向流里发一个 error 事件再正常收尾——错误也是流内事件，流总是完整结束。

    平台内部转换

    双路消费：每个 chunk 解析出 delta 文本后同时做两件事——拼接进全文缓冲（攒完整回复，供后续入对话历史、做决策解析）和推给实时消费者（旁路推送）。等流结束时同步阻塞收尾——整个 Agent Loop 跑在虚拟线程上，阻塞等待是廉价操作。

    事件总线多播：实时推送的终点是”LLM chunk”事件钩子，经事件分发器广播给所有监听器——SSE 推送只是订阅者之一，链路追踪和访问日志监听同一个钩子。流式输出与观测解耦：加观测不改推送链路。

    平台 → 上游客户端：SSE 监听器 + 对外协议

    服务端节流：LLM 每 token 产一条，但推理类 chunk 不需要逐条全推——按（会话、角色、轮次）维度设节流窗口，窗口内的 chunk 直接丢弃，只推窗口边界上的。丢的是中间帧不是语义：每帧同时携带增量文本和累计全文，客户端拿累计值渲染永远正确，丢中间帧只损失动画平滑度。

    统一信封帧协议：每个事件带 type/runId/timestamp/seq 公共字段，seq 从 1 递增，用于排序、去重、断点续传。事件类型按执行阶段分层：RUN_STARTED → 轮次/步骤开始 → THINKING（chunk 级）→ 工具调用/结果 → 步骤结束 → 评审决策 → 轮次结束 → FINAL_ANSWER → DONE。一个 run 的完整生命周期在帧序列里是可重放的状态机。

    单 sink 出口：所有事件源（chunk、工具调用、轮次状态、终态）都发往挂在运行上下文上的同一个 Sinks——单一出口天然保序，这是 seq 能全局递增而非各流独立的前提。

    上游客户端职责

    1. 流式读取，按空行切帧、解析 JSON；
    2. 按 type 分发渲染：THINKING 用累计全文做打字机、工具调用渲染工具卡、FINAL_ANSWER 是最终答案；
    3. 按 seq 去重——seq 非连续可能是服务端节流丢帧（正常），用累计值兜底即可；
    4. 断线重连带 runId + 最后 seq：run 还活着重新挂上多播，已结束查终态表直接给结果；
    5. 收到 DONE 帧才收尾——连接关闭不等于任务失败，ERROR 后仍要等 DONE，任务可能在后台继续跑；
    6. 重复 runId 会收到 409——幂等语义在协议层显式表达。

    三个设计决策

    阻塞读 + 虚拟线程，而非全响应式：消费方（Agent Loop）本来就是阻塞式循环——攒全文、跑工具、做多轮决策，中间套一层全响应式只会引入上下文传播的复杂度。管道里最贵的是端到端延迟，不是模型一致性，架构简单性优先。

    双 Sinks 分工：调用器内部的 Sinks 生命周期 = 单次 LLM 调用，解决”阻塞 IO → 响应式”的线程桥接；挂在运行上下文上的 Sinks 生命周期 = 整个 run，是对外公共出口。chunk 经事件总线从调用的私有管道汇入 run 的公共管道，多路订阅（推送、追踪、日志）各自独立。

    服务端节流 + 累计全文双保险：与其信任客户端处理高频流，服务端先降频且每帧带全量状态——丢帧容错从协议约定（客户端去重）下沉到数据设计（全量随帧），客户端逻辑更简单，渲染永远正确。

    断线了怎么办？事件怎么保证不丢？

    续传四步：

    1. 每条消息带递增序号：id: 137\ndata: {json}\n\n。id 用事件日志表里的自增主键或流内单调序号，必须在持久层有据可查（推流前先落日志，再推）——这是能续传的前提。
    2. 重连时客户端上报位点：浏览器 EventSource 自动带 Last-Event-ID: 137 请求头；自研客户端重连时带自己已确认的最后序号，等价。
    3. 服务端从位点之后补推：WHERE run_id=? AND seq > 137 ORDER BY seq。注意是严格大于——客户端说”我到 137”，就从 138 推起，137 这条无论客户端收全没收全都不重发。
    4. 客户端按 id 去重幂等合并：收到 id <= 已展示序号 的消息直接丢弃（防网络层重复投递）。

    架构级答案：

    • 断线重连：客户端带请求标识重连，服务端按 runId 从运行注册表找回活跃 run 的 Sinks 多播器重新订阅；如果 run 已经结束，走事件日志表回放已产生的事件。
    • 不丢的保证：SSE 是尽力而为的推送层，不是事实层。Source of truth 是 DB 里的状态机 + checkpoint。断线期间用户没收到的事件，最终状态一定会在重连或下次查询时对齐。这是”展示层可丢、事实层不丢“的设计原则。
    • 背压：SSE 推送配独立线程池，队列堆积满后让调用线程降级处理，避免无限堆内存。服务端消费 LLM 流塞进 Sinks 时同理——没有溢出策略（丢弃/缓冲）的 Sinks，堆积发生在你的内存里。

    落库粒度：不是每个 token 写一次库——token 级事件只在内存（Sinks 多播），轮次级进 checkpoint，终态进事实表。持久化频率与事实价值成正比：token 流是展示层（服务打字机体验），终态是事实层（服务正确性），续传只承诺事实层。event_log 式每 token 落表是理想形态的机制上限，生产常用”活跃 run 重订阅 + 终态表直给结果”的组合。

    Agent 场景的帧类型设计

    Agent 的 SSE 不是”推文本”，是推状态机。典型设计是三帧：

    帧 语义 data 处理
    Processing 还在干活，这是增量 结构化 payload，内容是文本片段
    Complete 本次请求到此为止 结构化，错误时带 errorCode
    Raw 下游说了什么我说什么 不解析不重组，透传

    三个设计讲究：

    1. 类型穷尽：用封闭类型定义帧，新增帧类型编译器强制所有消费点更新——协议演进有编译器兜底；
    2. Raw 是刻意的不对称：透传帧不进观测序列化逻辑，只打日志不组装 payload——”协议网关”和”协议终端”职责分离；
    3. 错误帧复用 Complete 而非单独 ERROR 帧：协议哲学是流总是以 complete 结束——客户端永远能预期”最后一个事件必是 complete”，用 errorCode 区分成败。这比让流中断优雅得多：连接层干净，业务语义全在帧里。

    配套细节：业务序列号写回每帧——SSE 协议原生没有顺序保证字段，聚合多事件流时必须自己造序列号，客户端才能检测丢帧/乱序。

    流式解析状态机（核心硬技能）

    LLM 输出是 token 流，但下游需要语义完整的单元（一段文本/一个 JSON 决策）。问题背景：模型输出要么是闲聊文本（文本），要么是结构化决策（{json}），stream=true 时你不知道开头是什么，直到看到第一个标签。

    四态状态机：

    DETECTING ──看到<reply>/<clarify>──→ STREAMING_TEXT ──看到</reply>──→ DONE
     │                                    │
     └──看到<task>/<dispatch>──→ BUFFERING_DECISION ──解析成功──→ DONE
                                        │
                                        └──解析失败──→ DONE（fallback）

    三个状态的行为差异是设计核心：

    • DETECTING（探测期）：chunk 攒进 buffer，找四种开标签中出现位置最早的（不是 first match 而是 earliest match，防模型输出两种标签）；没找到继续攒着不发射；
    • STREAMING_TEXT（文本直通期）：每个 chunk 直接找闭标签——找到则标签前内容全部发射进 DONE；没找到先找安全切点，安全部分发射，余量留在 buffer 等下一个 chunk。用户感知：首 token 延迟 ≈ 模型吐出开标签后第一个安全 chunk 的延迟，而非整个回复生成完；
    • BUFFERING_DECISION（决策缓冲期）：完全相反——chunk 只进 buffer 不发射，直到闭标签出现才把完整内容解析成决策对象一次性发射。结构化输出没有”半个 JSON”，宁可等齐。解析失败也有确定性出口（fallback 决策），不会卡死状态机；
    • DONE：后续 chunk 全部丢弃——闭标签后的任何输出（模型废话）不进入协议。

    flush() 是强制作答：流结束时无论停在哪个状态都收口——DETECTING 里没标签的裸文本当普通回复发（容错：模型没按格式输出也尽量给用户）；未闭合的决策缓冲走 fallback。状态机没有悬空状态。

    标签前缀扣留——chunk 边界安全切分：

    问题：chunk 可能把闭标签切成两半——模型输出 </reply> 时 SSE chunk 边界可能落在 </rep 和 ly> 之间，不假思索把整个 buffer 发出去，用户屏幕出现裸露的 </rep。

    解法：检查 buffer 尾部最长”闭标签长度减一”个字符，如果尾串是闭标签的前缀（如 </re 是 </reply> 的前缀），下一个 chunk 拼上来可能凑成闭标签——这部分扣在 buffer 里等判定；反之放心全发。最坏情况只是延迟一个 chunk，不是错误——流式容错的黄金标准。

    同类问题：UTF-8 多字节字符边界（字节级判断是否切在多字节字符中间则回退）。本质相同：流式/截断操作必须在语义原子的边界上落刀。

    保序与错误传播

    • 保序映射而非并发映射：状态机输出必须严格保序（文本增量顺序就是用户看到的文字），并发重排会打乱文本流；逐个顺序映射天然有序；
    • 半句话困境（流式系统独有的错误语义）：流中断时，错误处理策略取决于用户已经看见了什么——
      • 已发过文本 → 错误只能原样上抛：用户屏幕上已有半句话，静默换成 fallback 决策等于”话说到一半突然装作没说过”；
      • 没发过任何文本 → 才允许降级重答；
    • mid-stream 错误：HTTP 200 后网关在 data 里报 error_code——流已开始，不能当请求失败处理，转错误帧收尾；
    • 断连资源回收：客户端断连时响应式流自动把取消信号传播到上游 LLM 流订阅——最好的情况是取消传导到推理本身，直接省 token。

    超时与资源治理

    • 分级超时：SSE 长流只设 connect 超时不设 read 超时（read 超时会掐断正常长流），空闲超时用 heartbeat 间接覆盖；请求-响应式接口才有完整超时链（connect→read→总超时）。典型错误是给流式客户端配 read 超时，结果长推理全被掐断；
    • heartbeat/keepalive：代理（nginx 默认 60s）会掐断无数据的空闲连接，定期发注释帧 : ping\n\n 保活（几十字节）；
    • 并发控制：LLM 调用前的信号量拿不到许可直接拒绝不排队——SSE 场景每个挂起请求都占内存，排队是放大故障；
    • 全局兜底：Agent 整体耗时另有全局超时（如 2h），防止流挂死永远不结束。

    SSE vs HTTP 轮询

    这题比”SSE vs WebSocket”更本质——因为 SSE 场景里客户端的备选方案往往不是 WebSocket，而是普通 HTTP 轮询。答案要从”推”和”拉”的模型差异讲起。

    一句话：普通 HTTP 是”客户端反复问：好了吗？好了吗？”；SSE 是”服务端好了主动告诉你”。核心优势不是快，是实时性 + 请求成本 + 服务端视角的事件保真。

    1. 实时性：推送延迟 vs 轮询间隔

    轮询的延迟下限 = 轮询间隔。500ms 轮一次，平均延迟 250ms，最坏 500ms；想降到 50ms 就得 20 倍频率地打请求。SSE 的延迟 = 网络传输本身（毫秒级），LLM token 一吐出来就能推到用户屏幕上——打字机效果的”实时感”只有推送模型做得到，轮询出来的打字机是一顿一顿的卡帧。

    2. 成本结构：一次请求 vs N 次空转

    轮询 90% 的请求是无效的——”还没好？”→”没有”。每个无效请求都要走完整的 TCP/TLS 握手（或 keep-alive）、HTTP 头解析、鉴权、路由、日志——服务端为”什么都没发生”支付了全额处理成本。10 个连接 500ms 轮询 = 每秒 20 次空请求；1 万个连接就是每秒 2 万次。SSE 一次 GET 挂住，之后事件发生才有流量，无事件时只有心跳注释行（几十字节）。空闲成本对比是数量级的差距。

    3. 服务端视角：事件驱动的天然保真

    轮询模式下服务端要回答”现在到哪了“——必须把 token 流聚合成”当前快照”，每次轮询把快照发过去，客户端自己 diff 出新增部分。问题：

    • 服务端要维护快照状态（为轮询专门做一份”当前态”存储）；
    • 客户端 diff 有边界情况（两个轮询之间服务端更新了两次，diff 逻辑要处理乱序/重叠）；
    • 中间事件丢失——进度事件、错误事件这类瞬时消息轮询模型天然传不了，得另造”事件队列”让轮询来捞。

    SSE 是事件流原样下发：chunk 事件、进度事件、错误事件、终态事件按发生顺序逐条推，服务端只管”发生了什么就说什么”，不用维护快照，客户端 append-only 渲染。事件语义在传输层原生保留——chunk 序号、断线续传、半条消息丢弃，这套机制全部建立在”传的是事件而不是快照”上。

    SSE vs WebSocket vs UDP

    SSE vs WebSocket 的选型判断：LLM token 流是单向推送，SSE 走普通 HTTP（网关/鉴权/CDN 全兼容）；WS 是双向全双工。Agent 场景只有”插话/打断/多端同步”需要反向通道时才值得上 WS——需要打断语义、双向消息、重连 WAL 的主链路选 WS；纯输出流选 SSE。另注意 Streamable HTTP（MCP 新传输）把 SSE 变成了”POST 返回 SSE 流”的 RPC 响应编码——SSE 的角色从浏览器推送协议扩展到了服务间通信。

    为什么不用 UDP 代替 SSE：SSE 的”单向”之上还压着三个硬需求：

    1. 按序到达——token 流的顺序就是语义顺序，”巴黎/是/法国/首都”乱序到达就是乱码；
    2. 不丢——丢一个 chunk，用户屏幕就缺一块；
    3. 客户端地址可达——服务器要把数据推到客户端。

    UDP 三个都不保证。”都是单向”只解决了流量方向问题，没解决可靠性和有序性——而这两样恰恰是 TCP 已经做好的。真用 UDP，就得自己造丢包检测、重传、排序——那叫重新发明 TCP。

# ═══════════════════════════════════════════════════════════

def parse_request(conn: socket.socket) -> tuple[str, dict]:
    """读请求头直到空行（\r\n\r\n），解析出方法和路径。
    这就是'SSE 在字节流上切边界'的同一类问题：靠定界符切消息。"""
    buf = b""
    while b"\r\n\r\n" not in buf:            # 头部以空行结束
        chunk = conn.recv(4096)
        if not chunk:
            break
        buf += chunk

    head = buf.decode("utf-8", errors="replace")
    lines = head.split("\r\n")
    method, path, _ = lines[0].split(" ", 2)  # "GET /hello HTTP/1.1"
    headers = {}
    for line in lines[1:]:
        if ": " in line:
            k, v = line.split(": ", 1)
            headers[k.lower()] = v
    return method, {"path": path, "headers": headers}


def send_response(conn: socket.socket, status: str, body: bytes,
                  content_type: str, stream: bool = False) -> None:
    """写响应。两种模式：
    - 普通 HTTP：带 Content-Length，发完即关（客户端知道读多少字节）
    - 流式 HTTP（SSE 的原理）：不带长度，chunked 编码，连接保持"""
    if stream:
        headers = (
            f"HTTP/1.1 {status}\r\n"
            f"Content-Type: {content_type}\r\n"
            "Transfer-Encoding: chunked\r\n"     # 关键：长度未知，分块传输
            "Cache-Control: no-cache\r\n"
            "\r\n"
        )
        conn.sendall(headers.encode())
    else:
        headers = (
            f"HTTP/1.1 {status}\r\n"
            f"Content-Type: {content_type}\r\n"
            f"Content-Length: {len(body)}\r\n"   # 关键：告知确切字节数
            "Connection: close\r\n"
            "\r\n"
        )
        conn.sendall(headers.encode() + body)


def send_chunk(conn: socket.socket, data: bytes) -> None:
    """chunked 编码的一块：十六进制长度行 + 数据 + 空行。
    'HTTP在TCP字节流上切边界'的又一个实例。"""
    conn.sendall(f"{len(data):X}\r\n".encode() + data + b"\r\n")


def end_chunks(conn: socket.socket) -> None:
    """结束块：0 长度行，客户端据此知道流结束"""
    conn.sendall(b"0\r\n\r\n")


# ═══════════════════════════════════════════════════════════
# 两个端点：普通响应 + SSE 流式响应
# ═══════════════════════════════════════════════════════════

def handle(conn: socket.socket) -> None:
    method, req = parse_request(conn)
    path = req["path"]

    if path == "/hello":
        # 普通 HTTP：一次性响应，Content-Length 定长
        body = b'{"msg": "hello"}'
        send_response(conn, "200 OK", body, "application/json")
        conn.close()

    elif path == "/stream":
        # SSE：Content-Type 是 text/event-stream，连接不关，持续写
        send_response(conn, "200 OK", b"", "text/event-stream", stream=True)
        for i in range(1, 6):
            event = f"id: {i}\ndata: {{\"token\": \"tok-{i}\"}}\n\n".encode()
            send_chunk(conn, event)
            time.sleep(0.4)                 # 模拟 LLM 逐 token 生成
        end_chunks(conn)
        conn.close()
    else:
        send_response(conn, "404 Not Found", b"not found", "text/plain")
        conn.close()


# ═══════════════════════════════════════════════════════════
# 服务器主循环：TCP 监听 + 每连接一个线程
# （对比：FastAPI/uvicorn 是事件循环+协程；这里用线程简化，重点在协议）
# ═══════════════════════════════════════════════════════════

def serve(host: str = "127.0.0.1", port: int = 8714) -> None:
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # SOCK_STREAM = TCP
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind((host, port))
    srv.listen(16)                          # 内核排队等待 accept 的连接
    print(f"裸 HTTP 服务器已启动 http://{host}:{port}")
    print("测试: curl -N http://localhost:8714/hello")
    print("     curl -N http://localhost:8714/stream")

    while True:
        conn, addr = srv.accept()           # 三次握手已完成，拿到连接
        threading.Thread(target=handle, args=(conn,), daemon=True).start()


if __name__ == "__main__":
    serve()

    可观测与排障

    指标体系（SSE 链路的关键指标）：

    • 首 token 延迟：排队+prefill，用户体感的”响应快不快”就是它；
    • 总时长：decode 阶段。两者必须分开统计——慢在首 token 是容量/排队问题，慢在总时长是输出太长/模型问题，处置完全不同；
    • 流中断率、取消率（客户端主动断）、错误帧分布（按 errorCode 聚合）。

    排障场景清单：

    症状 根因 定位路径
    客户端 30-60s 后收到连接关闭 代理 read timeout 掐空闲连接 加 heartbeat 注释帧；调 proxy 配置
    半条消息/乱码 chunk 边界切在多字节字符或标签中间 查解析器是否有边界安全处理（标签前缀扣留 / UTF-8 回退）
    客户端丢帧 聚合多流时序号断号 查中间层是否丢事件；按序号补推
    服务端内存涨 Sinks 无界 buffer 堆积（客户端消费慢） 查背压策略（溢出时丢弃）
    僵尸连接 客户端死了服务端不知道，取消信号没触发 某些代理断连不传播 cancel；heartbeat 双向探测
