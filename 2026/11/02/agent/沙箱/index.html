    沙箱

    2026-11-02 2026-11-02 xinfan9 268 字 约 3 分钟

    一、定位：沙箱是Claw 的“工具执行器”

    Claw本身是一个无状态多用户服务，所有代码执行、文件操作、CLI 凭据（/root/userdata/.office-cli/）都不能落在自己进程里——需要一个按需启停、用户隔离、可销毁的执行环境。sandbox 就是这个环境的生命周期管家：

    Claw 管控（claw-manager）
        │ HTTP /sandbox/qwenclaw/*
        ▼
iagent-sandbox（本服务，Java 17 / Spring Boot 3.1）
        │ AgentBay SDK
        ▼
无影云沙箱（Session 即沙箱，一用户一沙箱）

    对上层暴露的语义很简单：/create-async 拿 sessionId → /executeCommand 跑命令 → /stop 销毁；/event-callback 接收外部健康检查系统的周期上报（约每沙箱每分钟 1 次）。

    二、核心机制一：异步创建 + 六态状态机

    /create-async 两条分发路径（这是整个服务最值得讲的设计）：

    • 快速路径：线程池队列有余量（绝大多数请求）→ 写 DB scheduling → 提交初始化任务 → 立即返回 sessionId/podId；
    • 溢出路径：队列满 → 写 DB created → 等待 QwenClawInitScheduler（10s 扫一轮，按 created_at 升序取 32 条）CAS 抢占后入队；

    状态机：created → scheduling → initializing → running / failed / stopped。所有流转都是定向 CAS 更新（如 markRunning 带 WHERE status='initializing' 守卫），文档里列为“关键约定”：禁止 save() 全量更新与异步初始化竞争——多节点并发只有一个成功，和 octopus-hub 恢复抢占 CAS（status+attempt+nodeIp 三字段联动）是同一套模式。

    初始化八步（工作线程执行）：CAS 到 initializing → reconnect → 写 supervisor 配置（openclaw 进程定义）→ 批量挂 OSS（单次 STS 鉴权 + “reached the maximum” 限流重试最多 5 次）→ 取 dashboardUrl → 执行 initCommands → supervisorctl update 启动 claw 进程 → CAS markRunning。任何一步失败 = 销毁 Session（防僵尸沙箱）→ CAS 标 failed → 驱逐 Redis → 通知管控，失败语义干净。

    通用能力烧在共享镜像里（静态层）、用户数据和配置通过 OSS 挂载进来（持久层）、个性化初始化靠 initCommands 在每次创建时执行（动态层）。沙箱本身是易失的（空闲 60 分钟就销毁），所以“个性化”的秘诀全在把可变部分外置到镜像之外。

    层 载体 生命周期 变更成本 放什么
    镜像 dockerImageId 静态，所有用户共享 高（重新构建镜像） 公共运行时/工具链
    OSS 挂载/Context storageConfigs 持久，跨沙箱存活 低（写入即持久） 用户数据/凭据/工作区
    initCommands 创建参数 每次创建重放 低（改参数即可） 个性化安装/启动命令

    超时兜底的顺序细节：TimeoutCleaner（30s 扫一轮，initializing 超 60s 判死）先 CAS markFailed 成功后才 destroySession——防止工作线程恰好 markRunning 后被误销毁；doInit 在长耗时步骤前主动 heartbeat 刷新 updated_at 防误杀。

    三、幂等：五道机制，各有分工

    “每次重建重放”的初始化要幂等，代码里实际落了五层：

    1. 状态机 CAS——宏观幂等（防重复初始化）

    每个沙箱实例只初始化一次的保证：markInitializing 带 WHERE status='scheduling' 守卫，多节点/调度器/工作线程同时抢，只有一个 CAS 成功；markRunning 带 WHERE status='initializing'——若已被 TimeoutCleaner 标 failed（CAS 返回 0），工作线程直接跳过不覆盖。“这个沙箱实例”级别的操作不会重复执行。

    2. 前置检查——挂载的幂等（防重复挂载出错）

    Step 5 Phase 1 有个精妙的分叉处理（L1304-1331）：

    • 挂载点在 /root/.openclaw 开头 → 先 rm -rf 清掉再挂——这是刻意为幂等设计的：该目录有历史残留（上次挂载的痕迹）时，删干净重来；
    • 其他挂载点 → 反向策略：目录已存在就整体失败（”mount point 已存在”→ markFailed + 销毁）——宁可失败也不悄悄重挂。

    这两条规则合起来是一套显式的幂等语义：要么环境是干净的（新沙箱，挂载点必然不存在），要么操作者明确清理（openclaw 目录强制删除）。挂载在 ossfs 语义下天然幂等（同一路径重复挂载结果是同一个 OSS 视图），但代码不依赖这个隐式性质，用前置检查把它变成显式契约。

    3. 失败即销毁——防“半成品状态”破坏幂等前提

    markFailedStatusAndDestroyFromInit 的顺序是先销毁 Session、再标 failed、再驱逐缓存。这意味着不存在“初始化了一半的沙箱被复用”的场景——下次重试面对的永远是全新容器（挂载点必然不存在、supervisor 配置必然是初始态）。幂等的前提是环境复位，销毁保证了复位。Phase 3 限流重试（”reached the maximum” 最多 5 次间隔 1s）只对单次挂载调用重试，整个初始化失败不重试——重来就是新沙箱。

    4. initCommands 的幂等——约定而非保证

    命令内容是管控侧生成的（如 pip install requests），服务侧只逐条执行并检查 exitCode（L1484-1485）。幂等责任在命令本身：pip/npm install 天然幂等（已装则跳过）；服务侧的保证是“执行环境每次都是新的”（第 3 点），所以幂等要求退化为“命令对干净环境的效果确定性”。反例也明确：非幂等命令（如 echo x >> file）在单沙箱生命周期内也不会重复执行（初始化只跑一次），跨重建因为环境复位也无累积效应。

    5. 数量校验——防 SDK 异常破坏不变量

    Phase 2 批量挂载后校验“返回结果数量 == 请求数量”（L1361-1369），不一致直接判失败——防止 SDK 部分返回导致的状态错认。这是把“不变量显式校验”作为幂等的组成部分：幂等不只靠执行逻辑，还靠对结果的完整性断言。
